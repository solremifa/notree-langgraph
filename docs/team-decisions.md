# worker 관련 팀 결정 사항

worker 뼈대(`notree/`)는 돌아가지만, 아래 값과 규칙은 **임시로 넣어 둔 제안값**입니다.
각 항목마다 무엇을 정해야 하는지, 선택지, 제안, 정하지 않으면 생기는 일을 적었습니다.

| # | 결정할 것 | 제안 | 급한 정도 |
|---|---|---|---|
| 1 | 재배송을 누가 하나 | worker가 `XAUTOCLAIM` + scheduler는 누락 복구만 | 높음 |
| 2 | rt/batch 시간 값 | rt 15/5/20초, batch 60/20/90초 | 높음 |
| 3 | 재시도 한도와 실패 처리 | rt 2회, batch 3회. 실패는 DB `failed` + 화면 표시 | 높음 |
| 4 | permit 토큰 | HMAC 서명 + 사용자 ID 포함 → MCP가 RLS에 사용 | 중간 |
| 5 | 동시 실행 수 | rt 4, batch 1 (프로세스당), 측정 후 조정 | 중간 |
| 6 | 배정기 누락 복구 | 30초 넘게 `reserved`/`sent`인 의도 다시 보내기 | 중간 |
| 7 | 실패한 작업 다시 하기 | 같은 job을 되살림 (체크포인트 유지) | 낮음 |
| 8 | MCP 도구 계약과 담당 | 핸들러 담당자가 자기 도구 입출력을 정의 | 높음 |
| 9 | 체크포인트 정리 | 완료 후 7일 보관 뒤 삭제 | 낮음 |

---

## 1. 재배송을 누가 하나

worker가 작업 도중 죽으면 그 메시지는 Redis에 "처리 중"(PEL)으로 남습니다. 누군가 이걸 다시 꺼내야 합니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. worker가 직접** (지금 뼈대) | 메시지를 읽기 전에 매번 `XAUTOCLAIM`으로 오래 방치된 걸 가져감 | Redis Streams의 표준 방식. 살아 있는 worker가 있으면 바로 처리. 코드가 한곳에 있음 | worker마다 매 바퀴 Redis 호출이 하나 늘어남 (무시할 수준) |
| B. scheduler 주기 작업 (설계서 표현) | scheduler가 주기적으로 `XPENDING` → 오래된 걸 `XCLAIM` 후 새로 `XADD` + 옛것 `XACK` | 재배송 정책(횟수·간격)을 한곳에서 통제 | scheduler가 죽으면 재배송도 멈춤. 메시지를 복사하는 과정에서 순서·중복을 다시 신경 써야 함 |

**제안: A.** 단, scheduler는 6번(배정기 누락 복구)을 맡습니다. 설계서 문구는 "worker가 방치된 메시지를 회수, scheduler는 의도-메시지 불일치 복구"로 고치면 됩니다.

정하지 않으면: 두 곳에서 동시에 재배송해 같은 작업이 두 번 시작될 수 있습니다. lease 덕분에 결과가 망가지지는 않지만 로그가 꼬입니다.

## 2. rt / batch 시간 값

값 네 개가 엮여 있습니다. **heartbeat < lease < 재배송 기준**, 그리고 **실행 제한 ≤ 사용자에게 약속한 시간** 이 규칙입니다.

| 값 | 뜻 | rt 제안 | batch 제안 | 설계서 |
|---|---|---|---|---|
| lease | heartbeat 없이 이만큼 지나면 "죽었다"고 봄 | 15초 | 60초 | 60초 |
| heartbeat | lease 연장 주기 (lease의 1/3) | 5초 | 20초 | 20초 |
| 재배송 기준 (claim_idle) | ACK 없이 이만큼 방치되면 다른 worker가 회수 | 20초 | 90초 | 없음 |
| 실행 제한 (job_timeout) | 작업 하나의 최대 실행 시간 | 90초 | 15분 | Q&A 90초 |

생각해 볼 점
- **죽은 뒤 다른 worker가 이어받기까지 = 재배송 기준 + 폴링 주기(최대 1초).** batch 90초면 사용자는 최대 1분 반을 더 기다립니다. 과목 노트는 괜찮지만, rt를 batch 값으로 두면 Q&A가 사실상 멈춥니다.
- **rt를 너무 짧게 잡으면** 네트워크가 잠깐 끊겼을 뿐인데 "죽었다"고 판단해 작업이 넘어갑니다. heartbeat 3번을 연속으로 놓쳐야 넘어가도록 1/3로 둔 이유입니다.
- **Q&A 90초 약속**: 실행 제한 90초 + 재시도 1회를 허용하면 최악의 경우 90 + 20 + 90 = 200초. 약속을 지키려면 (a) Q&A는 재시도하지 않거나, (b) 요청 시각 기준 마감을 payload에 넣고 핸들러가 남은 시간만큼만 실행하도록 해야 합니다. **제안: (b)**
- 실시간 요약은 다음 요약이 곧 또 오니까 재시도 가치가 낮습니다. 한도를 1로 둘지 같이 정합니다.

## 3. 재시도 한도와 실패 처리

**무엇을 재시도할지** (핸들러가 어떤 예외를 던질지)

| 재시도 (`RetryableError`) | 즉시 실패 (`FatalError`) |
|---|---|
| OpenAI 429 / 5xx / 타임아웃 | 입력 형식 오류, 필수 값 없음 |
| MCP 연결 실패 | 출처가 삭제됨 (세대 불일치) |
| 실행 제한 초과 | 권한 없음 (permit 거절) |
| 예상 못 한 예외 (버그일 수도 있음) | 핸들러 없음 (미구현) |

**정할 것**
- 작업 종류별 한도: 제안은 rt 2회, batch 3회. 실시간 요약은 1회.
- 재시도 간격: 지금은 lease를 반납하고 재배송 기준(rt 20초, batch 90초)만큼 기다렸다 다시 합니다. OpenAI 429가 많으면 간격을 점점 늘리는 방식(지수 백오프)이 필요할 수 있습니다. 처음에는 고정 간격으로 시작하고 측정 후 결정합니다.
- **실패를 사용자에게 어떻게 보이나**: DB의 `jobs.state = failed`, `fail_reason`이 근거입니다. 정할 것은 (1) 화면 문구, (2) 사용자에게 보여 줄 사유와 숨길 사유(내부 오류 메시지는 숨김), (3) 7번의 "다시 시도" 버튼 여부입니다.
- dead letter(실패 작업 보관함)는 따로 만들지 않고 `failed` 상태로 대신합니다. 운영자가 `failed` 목록만 보면 됩니다.

## 4. permit 토큰

job_start가 발급하고, worker가 이후 모든 MCP 도구 호출에 붙이는 "이 작업을 이 worker가 실행해도 된다"는 증명입니다.

**지금 뼈대**: `job_id.worker.만료.HMAC서명` 문자열. 서버가 서명·만료·job_id 일치를 확인. `NOTREE_REQUIRE_PERMIT=1`이면 없을 때 거절.

**정할 것**
1. **사용자 ID를 담을지 → 담아야 합니다.** MCP 서버가 permit에서 사용자 ID를 꺼내 `SET LOCAL app.user_id = …`로 RLS를 걸어야, worker가 다른 사용자 데이터를 읽는 실수를 DB가 막아 줍니다. 설계서의 "worker는 MCP로만, MCP는 RLS로"가 실제로 성립하려면 필수입니다.
2. **형식**: HMAC 문자열(지금, 단순) vs JWT(표준, 라이브러리 필요). 내부 전용이라 HMAC으로 충분하다고 봅니다.
3. **허용 도구 범위**: 작업 종류별로 쓸 수 있는 도구를 제한할지 (예: 채점 작업은 `note.publish` 못 부름). 처음에는 제한 없이, 도구 목록만 문서화.
4. **만료**: 시도마다 새로 발급되므로 `실행 제한 + 여유`면 충분. 제안: rt 5분, batch 30분.
5. **비밀키 관리**: 환경변수(`NOTREE_PERMIT_SECRET`) → 배포 시 GitHub Actions secret / 서버 `.env`. 키를 바꾸면 진행 중 작업의 permit이 무효가 되므로 배포 순서 주의.

## 5. 동시 실행 수

- **프로세스당 동시 실행(concurrency)**: 한 worker 프로세스가 동시에 돌리는 작업 수. rt는 대부분 OpenAI 응답 대기라 여러 개를 동시에 돌려도 CPU 부담이 적습니다 → 제안 4. batch는 작업 하나가 LangGraph 안에서 이미 병렬(`Send`)이라 → 제안 1.
- **worker 컨테이너 수**: 처음엔 rt 1개, batch 1개. 시연 규모면 충분합니다.
- **겹치는 제한 세 가지를 구분해야 합니다**
  1. 배정기의 사용자·과목별 동시 상한 (설계서: 강의당 실행 1·대기 1 등) — "한 사람이 독점하지 않게"
  2. worker의 concurrency — "한 프로세스가 감당할 만큼만"
  3. OpenAI 계정의 분당 요청·토큰 한도 — "외부 한도 넘지 않게"

  3번은 1·2로 간접적으로만 지켜집니다. batch의 extract 병렬 수까지 더한 **전체 동시 OpenAI 호출 수**를 계산해 보고, 넘치면 핸들러 공용 세마포어(`ctx.extras`)로 묶어야 합니다.

## 6. 배정기 누락 복구

배정기는 `허가(reserved) → XADD → 전송 완료(sent)` 세 단계를 거칩니다. 중간에 죽으면:

| 죽은 시점 | 상태 | 결과 |
|---|---|---|
| 허가 후, XADD 전 | DB `reserved`, Redis 메시지 없음 | **영원히 실행 안 됨** |
| XADD 후, 전송 완료 표시 전 | DB `reserved`, Redis 메시지 있음 | 실행은 됨. 복구 작업이 다시 보내면 메시지가 두 개 → 두 번째는 `job_start`가 done/leased로 걸러 냄 |
| worker가 `job_release` 후 메시지가 유실 (Redis 재시작 등) | DB `sent`, 메시지 없음 | **영원히 실행 안 됨** |

**제안**: scheduler 주기 작업으로 "`reserved` 또는 `sent`인 채로 30초 넘게 바뀌지 않은 의도"를 다시 XADD. 중복 메시지는 job_start가 안전하게 걸러 내므로 넉넉하게 다시 보내도 됩니다. 이를 위해 jobs 테이블에 `updated_at` 컬럼이 필요합니다.

## 7. 실패한 작업 다시 하기

사용자가 "다시 시도"를 누르면:
- **A. 같은 job을 되살림**: `failed → pending`, 시도 횟수 초기화. 과목 노트는 thread_id가 같으므로 **체크포인트에서 이어감** (이미 끝난 추출의 LLM 비용을 아낌).
- B. 새 job을 만듦: 처음부터. 단순하지만 비용이 다시 듦.

**제안: A.** 다만 실패 사유가 "출처 삭제" 같은 영구 실패면 되살려도 또 실패하므로, 다시 시도 버튼은 재시도 한도 초과·시간 초과로 실패한 경우에만 보여 줍니다.

## 8. MCP 도구 계약과 담당

worker 핸들러는 MCP 도구 없이는 아무것도 못 합니다. 도구가 핸들러 사이의 유일한 계약이므로 먼저 정해야 병렬로 개발할 수 있습니다.

**정할 것**
- 도구 이름 규칙: 설계서는 `notes.search`처럼 점. 지금 PoC는 `job_start`처럼 밑줄. 하나로 통일 (MCP 스펙상 둘 다 가능).
- 공통 인자: 모든 worker용 도구는 `permit`을 받는다. 쓰기 도구는 `idem_key`(= job_id)를 받는다.
- 공통 응답: 성공 `{ok: true, ...}`, 거절 `{ok: false, reason}`. 거절 사유로 FatalError/RetryableError를 판단할 수 있게 사유 코드를 정함 (`generation_mismatch` → Fatal, `busy` → Retryable 등).
- **담당**: 핸들러 담당자가 자기가 쓰는 도구의 입출력을 정의하고, MCP 서버 구현(PG 쿼리)은 같이 작성. 예: 노트 쪽 핸들러(실시간 요약·최종 노트·과목 노트)와 `transcript.range`·`summary.publish`·`note.publish`는 T3·T4, Q&A·채점과 `qa.*`·`grade.*`는 T5.

## 9. 체크포인트 정리

LangGraph는 단계마다 상태 전체를 저장하므로 과목 노트 작업 하나에 체크포인트가 10개 안팎 쌓입니다.

- 완료된 작업: 7일 보관 후 삭제 (오류 조사용). `checkpoint_delete_thread` 도구는 이미 있음 → scheduler 주기 작업에서 호출.
- 실패한 작업: 7번에서 되살릴 수 있어야 하므로 실패 후에도 같은 기간 보관.
- 사용자 탈퇴·과목 삭제 시: 삭제 원장 흐름(설계서 11절)에 체크포인트 테이블도 포함해야 합니다. **빠뜨리기 쉬우니 꼭 목록에 넣을 것.**
