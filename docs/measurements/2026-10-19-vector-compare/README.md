# 검색 방식 오프라인 비교 — pg_trgm · 벡터 · 결합 (2026-10-19)

## 결론

> 새 AI 생성 질문 세트에서 벡터 검색이 가장 높은 검색 성능을 보였습니다. 동일 비중 RRF는 개선하지 못했습니다.
> 다음 단계에서는 벡터 검색을 우선 후보로 실제 pgvector 경로에서 평가하고, 전사 문맥 확장과 질문별 실패 분석을 진행합니다.
> worker·그래프의 기본 검색 변경은 답변 품질 평가 후 결정합니다.

이번 단계에서 worker와 그래프는 바꾸지 않았다. 질문 장수가 작아(새 30 중 답할 수 있는 질문 26개, 1문항 ≈ 4%p) 방향만 본다.

## 질문 세트

| 세트 | 수 | 만든 방법 | 용도 |
|---|---|---|---|
| 기존 33 | 33 + 범위 밖 1 | 강의 구간 제목을 참고해 작성 | 지금 검색 방식을 다듬을 때 봄 (단어가 문서와 겹치기 쉬움) |
| 새 30 | 26 + 범위 밖 성격 4 | AI 생성. 기준값 조정에 쓰지 않음 | 이번 비교의 주 근거 |
| 실제 학생 질문 | — | 따로 수집 예정 | 아직 없음 |

새 30의 정답표는 항목별 근거 문서 ID를 적는다 (항목 50개). 정답표는 검색·답변이 끝난 뒤 채점에만 쓰고 LLM 입력에 넣지 않는다.

## 지표 정의

| 지표 | 정의 | 분모 |
|---|---|---|
| R@k 노트 / 전사 | 그 출처의 상위 k개 안에 정답 문서가 있는 질문 비율 | 정답 있는 질문 (기존 33, 새 26) |
| R@k 둘 중 하나 | 노트 상위 k ∪ 전사 상위 k (후보 최대 2k개) 안에 정답이 있는 질문 비율. 통합 상위 k가 아님 | 같음 |
| 항목@k (새 30) | 정답표 항목마다 그 항목의 근거가 노트 상위 k ∪ 전사 상위 k 안에 있는지 | 항목 50개 |
| 전달 근거 정답 포함률 | 그래프가 실제로 LLM에 넘긴 근거(모든 시도의 합)에 항목 근거가 있는지 | 항목 50개 |
| 답변 품질 | 기대 상태(completed / 부분 답변 / 근거 부족) 일치, 답변 인용 | 질문 30개 / 항목 50개 |

정답 판정은 문서 ID 일치이고 요약 노트 `s{n}`은 같은 구간의 전사 `t{n}`과 같은 근거로 센다. 정답표에 없는 동등 구간은 세지 않으므로 실제보다 낮게 잡혔을 **가능성**이 있다 (동등 근거 검토 전).

이전 기록의 "32/33"(`2026-10-17-pg-search`)은 노트 상위 3 ∪ 전사 상위 3(우선 강의 2개 → 0.3 미만이면 과목 전체 확장, kw_mean, LLM 검색어)에 정답이 있는 기존 33 질문 수다. 검색 단계 지표이고 전달 근거·답변 품질이 아니다.

## 1. 검색 품질 (칸 = 비율 · 개수)

### 기존 33 (분모 33)

| 방식 | R@3 노트 | R@3 전사 | R@3 둘 중 | R@5 노트 | R@5 전사 | R@5 둘 중 |
|---|---|---|---|---|---|---|
| trgm | 94% 31 | 88% 29 | 97% 32 | 97% 32 | 88% 29 | 100% 33 |
| 벡터 | 82% 27 | 76% 25 | 94% 31 | 85% 28 | 85% 28 | 94% 31 |
| 결합 | 88% 29 | 94% 31 | 100% 33 | 94% 31 | 94% 31 | 100% 33 |

trgm은 9개 질문에서 정답이 3위 경계의 동점에 걸려 있다(@5는 5개). 동점 순서만 바꿔도 전사 R@3가 79%↔88%로 움직였다. 지금 PG 검색도 동점 정렬 기준이 없다 (기록만, 이번에 고치지 않음).

### 새 30 (분모: 질문 26 · 항목 50)

| 방식 | R@3 노트 | R@3 전사 | R@3 둘 중 | R@5 노트 | R@5 전사 | R@5 둘 중 | 항목@3 | 항목@5 |
|---|---|---|---|---|---|---|---|---|
| trgm | 38% 10 | 27% 7 | 50% 13 | 50% 13 | 31% 8 | 62% 16 | 32% 16 | 38% 19 |
| 벡터 | 62% 16 | 23% 6 | **62% 16** | 65% 17 | 31% 8 | **69% 18** | **44% 22** | **50% 25** |
| 결합 | 46% 12 | 35% 9 | 50% 13 | 58% 15 | 35% 9 | 62% 16 | 36% 18 | 44% 22 |

- 두 세트에서 순위가 뒤집힌다. 기존 33은 구간 제목 기반이라 단어 일치에 유리했을 수 있어, 방식 선택의 근거로는 새 30을 본다
- 벡터의 이득은 주로 노트에서 났다 (R@3 노트 10 → 16). 전사는 세 방식 모두 R@5 8~9/26
- 전사가 약한 원인으로 짧은 조각(중앙 88자)과 STT 오류는 **유력한 가설**이다. 현재 조각 / 인접 전사를 묶은 구간 / 조각 검색 후 앞뒤 문맥 전달을 비교해야 확인된다

### 방식 간 이기고 진 질문 (새 30, R@3 둘 중 하나)

| 비교 | 둘 다 | 앞만 | 뒤만 | 둘 다 못 찾음 |
|---|---|---|---|---|
| trgm vs 벡터 | 9 | 4 | 7 | 6 |
| trgm vs 결합 | 10 | 3 | 3 | 10 |
| 벡터 vs 결합 | 12 | 4 | 1 | 9 |

- trgm과 벡터는 서로 다른 질문을 찾는다. 둘 중 하나라도 찾은 질문은 20/26이지만 동일 비중 RRF는 13/26에 그쳤다
- 벡터만 찾고 결합이 놓친 4개(fresh07·15·22·25): 벡터에서 정답이 노트 1~2위였고, 결합 후 4~7위로 내려갔다. 이 4개 모두 trgm 목록에서는 정답이 6위 이하이거나 20위 안에 없었다 — 이 질문들에서는 trgm 상위 문서가 결합 순위 앞쪽을 차지한 것으로 보인다
- 결합만 찾고 벡터가 놓친 1개(fresh01): trgm은 전사 1위, 벡터는 17위
- 질문별 순위 전체: [per-question-limit3.md](per-question-limit3.md) 1·2장

## 2. 그래프가 전달한 근거와 답변 (새 30, 지금 그래프 + trgm)

| | 근거 3개 | 근거 5개 |
|---|---|---|
| 기대 상태 일치 | 28/30 | 26/30 |
| 항목 근거가 전달됨 | 30% 15/50 | 36% 18/50 |
| 답변이 정답 근거 인용 | 28% 14/50 | 28% 14/50 |
| 모든 항목 근거가 전달된 질문 | 4/26 | 5/26 |
| 범위 밖 4개 중 거절(근거 부족) | 3 | 3 |

각 설정 1회 실행이라 3개·5개의 상태 일치 차이(2문항)는 LLM 판단 변동 범위일 수 있다. 의미 채점(채점표)은 아직 하지 않았다.

### 항목별 추적: 검색 vs 전달

검색 = trgm 상위 3 (노트 ∪ 전사, 과목 전체, 그래프와 같은 LLM 검색어) · 전달 = 그래프가 넘긴 근거 전체

| 구분 | 근거 3개 | 근거 5개 | 의미 |
|---|---|---|---|
| 검색 X · 전달 X | 33 | 31 | 검색 개선 대상 (그중 벡터 상위 3에는 있음: 10 / 10) |
| 검색 O · 전달 X | 2 | 1 | 선별·중단 조건 개선 대상 |
| 검색 X · 전달 O | 1 | 3 | 그래프(우선 강의·확장·추가 검색)로 얻음 |
| 검색 O · 전달 O | 14 | 15 | |

- 이번 세트에서는 그래프 단계의 손실(1~2개)과 보완(1~3개)이 작고, 놓친 항목 대부분은 검색 단계부터 없었다 → **검색 단계부터 항목 충족률이 낮아 검색 개선이 필요하다**
- 그래프가 노트만 검색하고 멈춘 질문은 8개였지만, 그 질문들에서 "검색 O · 전달 X" 항목은 근거 3개에서 1개, 5개에서 0개다. 앞서 보고에서 "노트에서 멈춤이 낮은 포함률의 주된 원인일 가능성"이라 했던 것은 이 추적으로는 **뒷받침되지 않는다** (trgm 전사 검색도 해당 정답을 찾지 못함)
- 질문별 표: [per-question-limit3.md](per-question-limit3.md) · [per-question-limit5.md](per-question-limit5.md) 3장

## 4. 시간 · 비용 (분리 기록)

| 구분 | 값 | 비고 |
|---|---|---|
| 검색 계산: trgm | 질문당 중앙 47~49ms | 로컬 PG, 노트+전사 각 20개 |
| 검색 계산: 벡터 | 질문당 중앙 1.3ms | **numpy 메모리 계산**. 실제 pgvector 지연과 직접 비교할 수 없음 |
| 외부 준비: 질문 임베딩 | 중앙 148ms · 최대 213ms · 64개 질문 2,795토큰 | API 왕복 포함 |
| 외부 준비: LLM 검색어 생성 | 중앙 911ms · 최대 2,573ms | 지금 그래프의 understand 호출 |
| 초기 색인 | 문서 1,097개 · 9.8초 · 165,599토큰 | 1회 |
| 전체 Q&A (지금 그래프) | 중앙 3.2초 · 최대 6.7~7.2초 | 근거 3개·5개 |

질문 임베딩을 understand와 병렬로 돌리면 준비 시간을 줄일 수 있지만 항상 숨겨지지는 않고, 관련 없는 질문까지 임베딩하면 불필요한 호출이 생긴다. understand의 역할이나 관련성 판단 위치가 바뀌면 전체 비교도 달라지므로 여기서는 세 시간을 분리해 두기만 한다.

## 한계

## 재현

```
uv run python -m notree.dev.qa_fresh_eval --load --llm fake
uv run python -m notree.dev.qa_fresh_eval --llm openai --limits 3,5 --out data/fresh/out/run-openai.jsonl --sheet data/fresh/out/sheet-openai.md
uv run python -m notree.dev.pgsearch_eval --load --scores kw_mean --keywords data/qa_keywords.json
uv run python -m notree.dev.vec_embed --model text-embedding-3-small --out data/vec/oai-3-small
uv run python -m notree.dev.vec_compare --check --emb data/vec/oai-3-small
uv run python -m notree.dev.vec_compare --emb data/vec/oai-3-small --fresh-keywords data/fresh/out/run-openai.jsonl --out data/vec/compare.jsonl
uv run python -m notree.dev.vec_trace --compare data/vec/compare.jsonl --run data/fresh/out/run-openai.jsonl --md data/vec/trace.md
uv run python -m notree.dev.vec_trace --compare data/vec/compare.jsonl --run data/fresh/out/run-openai.jsonl --limit 5 --md data/vec/trace-5.md
```

강의 원문·질문 문장·정답표·임베딩·질문별 문서 ID는 `data/`(git 제외)에만 있다. 이 폴더의 표는 질문 ID·순위·개수만 담는다.
