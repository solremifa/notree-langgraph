# Redis 소유 키 heartbeat 시험 (2026-10-18)

`tests/test_redis_ownership.py` — **실제 redis-server 7.0.15** (fakeredis는 Lua를 못 돌림). 성능 측정이 아니라 동작 확인입니다.
시간 설정은 줄였습니다: heartbeat 0.3초 < 소유 키 TTL 1.0초 < 재배송 기준 1.2초 (실제 설정과 같은 순서).

## 결과 (10개 통과, 3회 반복 모두 통과)

| 시험 | 보는 것 | 결과 |
|---|---|---|
| Lua: 현재 소유자만 갱신 | 갱신하면 키 TTL·방치 시간 초기화, 남의 토큰으로 해제 불가 | 통과 |
| Lua: 만료된 소유자 | 키가 만료돼 B가 잡은 뒤 A의 heartbeat → 거절(0), A의 해제 → B 키 그대로 | 통과 |
| Lua: 회수된 메시지 | B가 XAUTOCLAIM한 뒤 A의 heartbeat → 거절(-1), **PEL 소유자는 계속 B**, 키 연장 안 함 | 통과 |
| Lua: 원본 메시지 없음 | XDEL 뒤 heartbeat → 거절(-2), 키 연장 안 함 | 통과 |
| worker: 결과 처리 | 성공·영구 실패·1번 실패 후 성공(반납 → 재배송 → 키 재획득)·한도 초과. **job_heartbeat 호출 0번**, 남은 키·메시지 0 | 통과 |
| worker: 죽은 worker 인계 | course_update 중 A 죽음 → B가 이어받아 체크포인트에서 계속 (끝낸 단계 다시 안 함), 실행 세대 2 | 통과 |
| worker: 느리지만 살아 있음 | LLM 호출 하나가 재배송 기준보다 김(1.6초) → B가 가져가지 않음, 시도 1번 | 통과 |
| worker: heartbeat 지연 | A의 heartbeat 하나가 2초 늦음 → 키 만료·회수 → 2번째 시도가 세대를 올림. 첫 시도는 소유권 잃고 멈춤, 완료 1번 | 통과 |
| 프로세스: SIGKILL | MCP 서버(HTTP)·배정기·worker를 따로 띄우고 A를 강제 종료 → B가 이어받음 | 통과, **1.3~2.1초** |
| 프로세스: SIGSTOP → SIGCONT | A 프로세스 전체를 멈춤 → B가 이어받음 → A를 깨움 | 통과. 깨어난 A는 다음 heartbeat에서 "소유권을 잃음 → 작업 취소", 저장·ACK 없음 |

인계 시간은 재배송 기준(1.2초) + B 프로세스 기동 시간입니다. 실제 설정(rt 재배송 20초, batch 90초)에서는 그만큼 길어집니다.

## 시험하면서 본 것

- heartbeat 지연 시험에서 A의 메시지 받기 루프는 살아 있어서, B보다 A가 먼저 메시지를 다시 회수했습니다. A 안의 "이미 실행 중" 보조 방어가 막았고, 이 회수가 방치 시간을 다시 0으로 만들어 인계가 회수 기준 한 번만큼 늦어졌습니다. 안전 문제는 아니고, 2번째 시도를 A가 맡았습니다.
- 프로세스 전체가 멈추는 실제 상황은 SIGSTOP 시험이 봅니다. 이때는 A가 아무것도 못 하므로 B가 넘겨받았습니다.
