# Q&A 실제 OpenAI 측정 (2026-10-17)

`notree.dev.qa_eval`: **가짜 검색**(`sample_corpus`, 키워드 일치) + **실제 LLM**. 주어진 근거로 답하는 능력을 보며, 실제 검색 품질은 측정 대상이 아닙니다.

- 비용은 단가를 넣지 않아 계산하지 않음 (질문당 입력 약 120~390, 출력 약 35~77 토큰).

**partial 실패 원인** ("스택과 큐는 어떻게 다르고 각각 언제 써?"). 3회 모두 같은 모양:

```json
{"status": "부분 답변", "citations": ["n1"], "searched": ["note", "transcript", "web"],
 "answer": "스택은 LIFO 구조로, 마지막에 넣은 원소를 먼저 꺼낸다. [^n1]",
 "llm": [{"kind": "understand", "seconds": 1.121, "prompt_tokens": 160, "completion_tokens": 25},
         {"kind": "answer#1", "seconds": 0.794, "prompt_tokens": 216, "completion_tokens": 43}]}
```

- 기대: 스택 LIFO(n1) + 큐 FIFO(n2) + 큐는 대기열(t2), 스택의 쓰임새는 근거가 없으니 `부분 답변`.
- 실제: 스택 한 문장만 쓰고 "근거가 더 필요"로 끝냄. 상태(`부분 답변`)는 맞지만 **답할 수 있는 부분(큐)까지 빠뜨림** → 프롬프트 문제로 판단.
- 1차 판단: 프롬프트 문제로 보고 답변 프롬프트에 "여러 부분으로 된 질문은 부분마다 따져서 답할 수 있는 부분은 빠짐없이" 추가.
  측정 도구가 실패한 사례의 검색어·근거(점수)·문장별 인용을 출력하도록 고침. → **이 판단은 2차 측정에서 틀린 것으로 확인됨 (아래).**

전체 18/21 · 질문당 중앙 1.65초 · LLM 39번(호출당 중앙 0.84초) · 토큰 입력 7,641 / 출력 1,288 (21건 합계).
프롬프트가 길어져 근거가 있는 사례의 입력 토큰이 질문당 약 100 늘었음 (362 → 465).

**partial의 진짜 원인** — 새로 남긴 검색어·근거로 확인:

```
검색어=['스택', '큐', '데이터 구조', 'LIFO']  근거=[('n1', 0.5), ('n2', 0.25), ('t1', 0.25), ('t2', 0.25)]
- 스택은 LIFO 구조로, 마지막에 넣은 원소를 먼저 꺼낸다.  ['n1']
```

- 모델이 프롬프트("띄어쓰기가 있는 구는 단어로 나눠")와 달리 `'데이터 구조'`를 한 덩어리로 냄 → 어디에도 안 맞음.
- 가짜 검색 점수는 "검색어 중 몇 개가 들어 있나"라 n2·t1·t2가 0.25점 → LLM에게 넘기는 기준(`EVIDENCE_MIN` 0.3) 미만 → **LLM은 n1만 받았음**.
  n1만으로 스택만 답하고 "근거 더 필요"라고 한 건 맞는 동작. 프롬프트 문제가 아니었음.
- 조치: 코드가 검색어의 띄어쓰기를 단어로 나눔(`split_keywords`). 같은 검색어면 `['스택','큐','데이터','구조','LIFO']` → n1 0.6, n2 0.4로 n2가 근거에 들어감 (테스트 `test_spaced_keywords_are_split_into_words`).
- 1차에 넣은 "여러 부분 질문" 프롬프트 문구는 남겨 둠 (근거가 있는데 한 부분만 답하는 경우를 막는 문구라 해는 없음. 비용은 답변 1회당 입력 약 100토큰). 효과는 아직 확인 안 됨.
- 이 실패는 **가짜 검색 점수 방식 때문에 크게 드러난 것**이기도 합니다. 실제 검색(pg_trgm)은 점수 방식이 달라서, 검색어 처리는 PG 연결 때 다시 봐야 합니다.

**결정 (2026-10-17)**: 시간이 없어 검색을 하나도 못 했으면 `근거 부족` 대신 `시간 초과`(`notice_code=timeout`)로 저장합니다.
일부라도 실제로 검색했으면 기존대로 `근거 부족`입니다. `qa_eval`의 `tight_deadline` 기대값도 `시간 초과`로 바꿨습니다. → 3차 측정 대기.

- partial은 이제 스택(n1)과 큐(n2)를 모두 답하고, 근거가 없는 "스택을 언제 쓰나"만 남겨 `부분 답변`.
- **대신 partial은 LLM 4번(상한), 약 5초, 입력 토큰 2.5배.** 노트 점수가 충분해(n1 0.6) 노트에서 멈춘 뒤, LLM이 "근거가 더 필요"하다고 해서 전사 → 웹까지 차례로 더 찾고 매번 다시 답했기 때문입니다 (설계대로의 동작, 보완 목록 8번).
  더 찾을 출처에서 새 근거가 안 나와도 다시 답하므로, 여러 부분 질문이 많으면 비용이 커집니다. 새 근거가 없으면 다시 답하지 않는 최적화를 검토할 만합니다.
- 이 측정이 확인한 것은 **주어진 근거로 답하는 능력**입니다. 실제 검색 품질(근거 검색 성공률)은 실제 강의 데이터·PG 검색으로 따로 잽니다.

### 평가 기준 정정 (3차 이후, 리뷰 반영)

- **"문장 안 인용 표시 0"은 모델이 지시를 지켰다는 뜻이 아니었습니다.** 1~3차의 검사는 그래프가 정제한 뒤의 문장을 봤으므로, 확인한 것은 "사용자에게 가는 본문이 깨끗하다"입니다.
  모델이 `[n1] [^n1]`을 넣어도 정제 후에는 통과합니다 (`test_model_markers_are_caught_before_cleaning`).
  이제 `model_no_markers`(LLM 원본)와 `delivered_no_markers`(정제 후)를 따로 봅니다. **모델 준수 여부는 4차 측정에서 처음 확인됩니다.**
- **기대 상태를 사례마다 하나로 좁혔습니다.** `not_found`는 `근거 부족`만(일반 지식·completed면 실패), `partial`은 `부분 답변`만(completed면 실패).
  3차 결과는 바뀐 기준으로도 통과입니다 (not_found 6/6 근거 부족, partial 6/6 부분 답변).
- **42/42는 같은 7개 질문을 반복한 자동 검사 결과입니다.** 일반적인 답변 정확도 100%를 뜻하지 않습니다.

**함께 본 것 (2차 이후 결정됨)**: `tight_deadline`(마감 4초)은 기대 범위라 통과했지만, 시간이 없어 검색을 하나도 안 했는데 `근거 부족`으로 저장됩니다.
사용자에게는 "자료에 답이 없다"로 보이므로, 검색을 모두 시간 때문에 건너뛰고 인용이 없으면 `시간 초과`로 저장하는 쪽을 제안했습니다.
