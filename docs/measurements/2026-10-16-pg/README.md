# PostgreSQL 부하 측정 원본 (2026-10-16, 2026-10-17 일부 재측정)

재현 도구와 방법: [notree/dev/pgload/README.md](../../../notree/dev/pgload/README.md).
환경: PostgreSQL 16, 2 vCPU · 8GB (부하 생성기도 같은 머신), 합성 데이터 256만 행(어휘 약 110개).

| 파일 | 내용 | 측정일 |
|---|---|---|
| `sweep.jsonl` | 사용자 50~800명 × naive/fixed, 각 60초 (`loadgen.py`) | 10/16 |
| `sweep.log` | 위 실행 시각 기록 | 10/16 |
| `lanes.jsonl` | fixed + Q&A 전용 슬롯 8·16개 (`--qa-lane`) | 10/16 |
| `qa_burst.txt` | 질문 500개 동시, course/lecture 각 3회 | **10/17 재측정** |
| `transcript_bench.txt` | 녹음 2,000개·560개, per_session/grouped (per_session 2,000은 3회) | **10/17 재측정** |

`sweep.jsonl` 필드: `tps`(초당 커밋), `rows_upd_s`(초당 UPDATE 행), `wal_kb_s`, `pg_cpu_pct_of_2`(2코어 중 PG CPU %),
`client_cpu_pct_of_2`(부하 생성기), `active_avg`(일하는 연결 평균), `backlog_max`/`backlog_end`(밀린 작업), 그리고 작업 종류별 지연.

## 10/17 재측정에서 달라진 것

10/16 문서 수치 중 콘솔에만 찍고 파일로 남기지 않은 두 측정을 같은 데이터로 다시 돌렸습니다.

| 항목 | 10/16 문서 | 10/17 재측정 | 판단 |
|---|---|---|---|
| Q&A 검색, 질문 500개 동시 (course) | 14.6초, 34개/초 | 16.4~18.5초, 27~31개/초 | 같은 경향. 문서 값이 조금 낙관적 |
| 같은 조건 (lecture 우선 2개) | 4.2초, 120개/초 | 4.2~4.9초, 102~118개/초 | 같은 경향. 약 3.5~4배 |
| 전사 저장, 녹음 2,000개 per_session | 트랜잭션 3,760/s, PG CPU 38%, **p99 2.5초** | 3,357~4,060/s, 26~34%, **p99 0.12~4.2초** | 트랜잭션·CPU는 재현. **p99는 실행마다 크게 흔들림** (3회 중 1회만 4.2초) |
| 같은 조건 grouped | 7/s, 5%, p99 약 340ms | 7.1/s, 5.7%, p99 374ms | 재현 |

- p99가 흔들리는 원인은 확인하지 않았습니다 (체크포인트·autovacuum·같은 머신의 부하 생성기 후보). "per_session은 꼬리 지연이 가끔 초 단위로 튄다" 정도로만 읽어야 합니다.
- 전사 2,000개는 동시 녹음 2,000개 상황입니다. 800명(녹음 560개) 기준 per_session은 p99 7.8ms, PG CPU 10%였습니다.

## 이 수치로 말할 수 있는 것 / 없는 것

- 말할 수 있음: 이 구조에서 상대적으로 무엇이 무거운지 (전사 커밋 횟수, 과목 전체 trgm 검색, 공용 큐), 대책의 방향과 대략적 배율.
- 말할 수 없음: 운영 환경 절대 수치. 합성 데이터는 어휘가 작아 검색이 실제보다 무거울 수 있고, 실제 LLM 지연·Redis·네트워크·장시간 VACUUM 영향이 빠져 있습니다.
- **검색 범위 축소의 품질(근거 검색 성공률)은 이 데이터로 잴 수 없습니다.** 실제 강의 노트·전사가 필요합니다.
