# 2026-10-19 실행 시작 절차: Redis 선점 → DB 조건부 승인 (`feat/redis-liveness-default`)

`NOTREE_LIVENESS=redis`를 기본 구조로 완성하면서 **실행 시작 절차**를 바꿨습니다.
수용 조건을 통과해 기본값을 `redis`로 바꿨고, `db`는 명시적으로 고르는 비교·호환 모드로 남깁니다 (자동 전환 없음).
측정·시험 기록: [measurements/2026-10-19-start-protocol](../measurements/2026-10-19-start-protocol/README.md)

## 1. 고친 문제 (수정 전 Redis 모드에서 재현)

같은 `live_summary` 작업(총 1회)의 중복 메시지를 A·B가 받음 → A의 `job_start`는 DB에 반영됐지만 응답이 늦어 A가 아직 소유 키를 못 씀
→ B도 키가 없는 것을 보고 `job_start` → **두 시작이 모두 시도 횟수를 씀** → B는 시도 2 > 한도 1이라 요약 함수를 부르지 않고 실패 확정.

| 강제 순서 시험 (`tests/test_start_protocol.py`) | 상태 | 시도 | 요약 함수 | 저장 |
|---|---|---|---|---|
| DB 모드 (수정 전·후) | done | 1 | 1 | 1 |
| Redis 모드 수정 전 (`969ba03`) | **failed** | **2** | **0** | **0** |
| Redis 모드 수정 후 | done | 1 | 1 | 1 |

원인은 순서 하나가 아니라 경계였다: "살아 있는 실행이 있나"(Redis)를 본 뒤 "세대 발급·시도 계산"(DB)을 하는 사이가 원자적이지 않고,
DB의 시작은 무조건 세대를 올리고 시도를 셌다. 시도 계산 위치만 옮기거나 Redis·DB 순서만 뒤집으면 리뷰 2·3차에서 본
"키 만료 뒤 새 실행이 시작됐는데, 이전 worker의 늦은 DB 시작이 새 실행을 덮는" 문제가 돌아온다.

## 2. 고른 절차

```
1. Redis 선점   SET notree:own:{job} "{토큰}|{stream}|{msg_id}" NX PX ttl
                실패 → 다른 실행(또는 시작 중인 선점)이 있음 → DB를 부르지 않고 손대지 않음 (ACK 안 함)
2. DB 승인      job_start(start_id=토큰, expect_epoch=E, lease_sec=0, dispatch_gen)
                E는 처음엔 0. DB는 한 트랜잭션에서:
                  끝난 작업 → done/failed, 이전 전달 세대 → stale_dispatch     (기존 그대로)
                  같은 start_id로 이미 승인됨 → 같은 승인을 다시 돌려줌 (replay, 세대·시도 그대로)
                  exec_epoch ≠ E → superseded (현재 세대만 알려 줌. 아무것도 바꾸지 않음, 시도 안 셈)
                  exec_epoch = E → 승인: exec_epoch = E+1, attempts + 1, start_id 기록
3. superseded   소유 키가 아직 내 것인지 heartbeat Lua로 확인(연장) → 내 것이면 E = 알려 준 세대로 2를 한 번 더
                내 것이 아니면 손 뗌. 세 번까지
4. 실행         승인을 받은 뒤 핸들러. heartbeat는 지금처럼 Lua 한 번 (키 값 비교 + PEL 소유 확인 → 키 TTL·메시지 방치 시간 갱신)
                1~3 동안에도 같은 heartbeat가 돌아 DB 응답이 느려도 키가 만료되지 않는다
5. 해제         키 값(토큰) 비교 후 삭제. 죽은 worker는 TTL로 풀림
```

### 왜 안전한가 (원자성 경계)

- **Redis 원자 단위**: 선점(`SET NX PX`), heartbeat Lua(값 비교 → PEL 소유 확인 → XCLAIM JUSTID → PEXPIRE), 해제 Lua(값 비교 → DEL).
- **DB 원자 단위**: `job_start` 한 트랜잭션(`BEGIN IMMEDIATE`)에서 상태 확인·replay·세대 비교·승인. 모든 쓰기 도구는 permit의 세대를 같은 트랜잭션에서 비교.
- 두 저장소를 묶는 원자 연산은 없다. 대신 다음 성질로 맞물린다.
  1. 소유 키 값의 토큰은 선점마다 새로 만들고, 키는 `SET NX`로만 생긴다 → **"내 값이 지금 있다" = 선점한 때부터 지금까지 끊김 없이 내 것**.
  2. 승인은 `exec_epoch = E`일 때만 일어난다. E는 0(아직 승인된 실행이 없음)이거나, **키를 계속 가진 상태에서 DB에게 들은 값**이다
     (들은 뒤 키가 아직 내 것인지 확인). 그 세대의 실행자는 그때 키를 갖고 있지 않았다 → 이미 살아 있는 실행이 아니다.
  3. 따라서 키를 가진 실행(살아 있는 실행)은 누구도 E로 지목할 수 없다 → **살아 있는 실행을 쫓아내는 승인은 없다**.
     쫓겨나는 것은 키를 잃은 실행뿐이고, 그 실행의 쓰기는 기존대로 DB 세대 비교로 거절된다.
- 리뷰 2·3차의 경우:
  - A가 선점 → 멈춤(키 만료) → B가 선점·승인(1)·실행 → A가 깨어나 `expect=0`으로 시작 → `superseded` → A의 키 확인 실패 → 손 뗌. B 그대로.
  - A의 시작이 Redis 초기화를 건너 늦게 도착해도 같다 (세대는 DB에만 있고 초기화로 되돌아가지 않음, E가 맞지 않으면 아무것도 바꾸지 않음).
  - 시계에 기대지 않는다 (TTL 판단은 Redis 한 곳의 시계, 승인 판단은 DB의 세대 비교).

### 세 가지 수를 구분한다

| | 뜻 | 어디서 | 언제 오르나 |
|---|---|---|---|
| 전달 세대 `dispatch_gen` | 어느 Redis에 보낸 메시지인가 | DB `meta`·`jobs` | Redis 유실을 발견할 때 (기존 그대로) |
| 실행 세대 `exec_epoch` | 지금 쓰기를 허락받은 실행 | DB `jobs` | 승인할 때만. replay·superseded·중복 선점은 올리지 않음. 사용자 재시도·Redis 초기화로 되돌아가지 않음 |
| 업무 시도 `attempts` | 실행 승인을 확정한 횟수 (시도 한도 판단) | DB `jobs` | 승인할 때만. 사용자 '다시 시도'(`job_retry`)는 0으로 |
| 재배송 횟수 | 같은 메시지가 다시 전달된 횟수 | Redis PEL `times_delivered` | XAUTOCLAIM마다 (시도와 무관) |

### 시도를 쓰는 경우와 안 쓰는 경우 (정책)

- 안 씀: 중복 메시지·선점 경쟁에서 진 요청(DB 호출 자체가 없음), `superseded`, 같은 `start_id`의 재요청(응답 유실 뒤 다시 보냄), 끝난 작업·이전 전달 세대.
- **씀 (경계 — 정책으로 받아들임)**: DB가 승인을 확정한 뒤 핸들러를 끝내지 못하고 worker가 죽거나 멈춘 경우, 승인 응답을 끝내 받지 못한 경우,
  승인 직후 키를 잃은 경우(프로세스 정지가 TTL보다 길 때). 승인은 확정됐고 그 뒤 무슨 일이 있었는지 DB는 모른다 —
  외부 호출(LLM)을 했을 수도 있으므로 **시도로 센다**. 실시간 요약(총 1회)은 이 경우 실패 확정되고(결과가 저장돼 있으면 완료), 사용자 '다시 시도'나 후속 요약이 이어서 처리한다.
- 외부 LLM 호출이 정확히 한 번이라고 보장하지 않는다. 보장하는 것은 "중복 전달·경쟁 때문에 시도를 쓰지 않는다", "낡은 실행의 저장은 거절된다",
  "결과 저장은 idem_key로 한 번"이다. 승인 뒤 죽은 실행이 LLM을 불렀다면 이어받은 실행이 다시 부를 수 있다 (체크포인트가 있으면 끝낸 단계는 건너뜀).

### 실패할 때 복구

| 상황 | 결과 |
|---|---|
| 선점 응답 유실 (키는 써짐) | worker는 실패로 보고 손 뗌 → 키는 TTL로 풀림 → 재배송. 시도 안 씀 |
| DB 시작 응답 지연 | 그동안 heartbeat가 키를 연장 → 다른 worker는 선점 실패. 응답이 오면 실행 |
| DB 시작 응답 유실 | 같은 `start_id`로 다시 보냄(간격 0.2·0.5초) → replay. 끝내 못 받으면 키 해제·ACK 안 함 → 재배송 때 superseded → 새 승인 (시도 1 씀: 경계) |
| heartbeat 응답 유실·Redis 지연 | TTL 안이면 다음 박동에 다시. TTL을 넘기면 작업 취소 (기존 그대로) |
| 해제 응답 유실 | 키가 TTL까지 남음 → 그동안 다른 선점이 실패할 뿐 |
| worker 강제 종료·정지 | 키 만료 → 재배송 → superseded → 새 승인 (죽기 전 승인은 시도 1로 셈). 깨어난 낡은 실행은 heartbeat·저장에서 거절 |
| Redis 재시작·초기화 | 키가 사라져 진짜 실행자도 heartbeat에서 잃음. 복구가 새 전달 세대로 다시 보내고, 새 승인이 이어서 실행 (재실행 비용). 늦게 도착한 이전 세대 시작은 stale_dispatch |

## 3. 계약 변경

`job_start` (선택 인자 추가, 기존 호출은 그대로 동작):
- 입력 `start_id`: 이 시작 요청의 식별자. 같은 값으로 다시 보내면 이미 승인된 것을 그대로 돌려줌 (`replay=true`)
- 입력 `expect_epoch`: 이 값이 현재 `exec_epoch`와 같을 때만 승인. 다르면 `status="superseded"` + 현재 `exec_epoch`
- 출력 `status`에 `superseded` 추가, 출력 `replay` 추가
- `jobs.start_id` 컬럼 추가

worker 내부: `Ownership.held()·acquire(epoch)` → `Ownership.claim()` (세대 비교 Lua 삭제). `RedisLease(cfg, own)`.

## 4. 기본값

`NOTREE_LIVENESS` 기본 `redis`. `db`는 `NOTREE_LIVENESS=db`로 명시할 때만 (비교·호환). Redis 장애 때 DB 모드로 자동 전환하지 않는다 —
생존 판정이 두 곳이면 서로 다른 답을 낼 수 있어서다. Redis에 닿지 못하면 실행 중 작업은 TTL 뒤 멈추고, 새 작업은 Redis가 돌아올 때까지 시작하지 않는다.
