# 2026-10-17 변경 정리: Q&A 검색을 PG로, 전사 우선 검색 단계 (`feat/qa-pg-search`)

측정: [measurements/2026-10-17-pg-search](../measurements/2026-10-17-pg-search/README.md). 실제 강의 7개·질문 33개(Claude 초안)에서 얻은 **잠정** 설정입니다.

## PG 검색 어댑터 (`notree/mcp_server/pg_search.py`)

- `NOTREE_QA_SEARCH=pg`(기본 `sqlite`)면 `qa_search`가 PostgreSQL `qa_search_docs`를 읽고, `qa_seed`가 노트·전사를 거기에도 넣습니다. 접속은 `NOTREE_PG_QA_DSN`.
- 점수 kw_mean = 검색어별 `word_similarity(검색어, 본문)` 평균. 범위 = 사용자 + 과목 + 출처 + (선택) 강의 목록, `deleted_at`이 있는 문서 제외.
- 사용자·과목 확인과 삭제된 질문은 기존처럼 질문 행(SQLite)으로 먼저 거릅니다. 출처 ID·강의 ID를 그대로 돌려줍니다.
- PG 연결 실패·시간 제한은 `unavailable`(다시 시도 가능) → 그래프가 1번 다시, 안 되면 다음 출처.
- DB는 "범위 안 문서를 점수와 함께 읽기"만 합니다. 어느 강의를 먼저, 언제 넓힐지는 그래프가 정합니다 (DB는 CRUD만).
- 범위 안 문서마다 점수를 계산합니다(1,100개에서 질문당 약 40~100ms). 큰 규모에서는 trgm 인덱스로 후보를 먼저 줄이고, 정답이 잘리지 않는지 지금 방식과 비교해야 합니다.

## PG가 느릴 때 (리뷰 반영)

리뷰 지적 두 가지에 더해, 고치는 중에 하나를 더 찾았습니다. 셋 다 수정 전 코드로 재현했습니다 (PG 테이블을 잠가 검색을 막은 상태).

| 문제 | 수정 전 | 수정 |
|---|---|---|
| 호출 기록(`_log`)을 쓴 SQLite 트랜잭션을 연 채 PG를 기다림 | 다른 연결의 쓰기가 `database is locked` | 질문 확인·기록 트랜잭션을 커밋하고 닫은 뒤 PG 조회. 검색 뒤 삭제·수정은 `qa_complete`가 세대·실행권으로 다시 확인 |
| PG 연결·쿼리에 시간 제한 없음 | 그래프가 8초에 기다리기를 그만둬도 서버 쪽 쿼리는 잠금이 풀릴 때까지 계속 | `connect_timeout` 2초, `statement_timeout` 5초 (잠금 대기 포함, 그래프 8초보다 짧게). `NOTREE_PG_QA_CONNECT_TIMEOUT_SEC`·`NOTREE_PG_QA_STATEMENT_TIMEOUT_MS` |
| FastMCP(1.30)는 동기 도구를 이벤트 루프에서 바로 실행 | 검색이 PG를 기다리는 동안 **같은 MCP 서버의 모든 도구**(heartbeat 포함)가 멈춤 — 1초 안에 응답 못 함 | `qa_search`를 async로, PG 호출은 스레드로. `guarded`가 async 도구도 감쌈 |

시험 (`tests/test_qa_pg_search.py`)
- 느린 PG: 검색이 기다리는 동안 같은 서버의 `job_heartbeat` 0.5초 안 응답, 별도 SQLite 연결의 쓰기 성공, 검색은 1.5초 제한으로 끊겨 `unavailable`
- 응답 없는 PG(연결만 받고 말이 없는 서버): 5초 안에 `unavailable`

남은 주의
- 스레드로 넘겨도 동시에 도는 PG 검색 수는 기본 스레드 풀 크기까지입니다. 실제 배치에서는 연결 풀과 같이 정해야 합니다.
- 연결 풀러(pgbouncer 트랜잭션 모드 등)를 쓰면 접속 옵션의 `statement_timeout`이 안 먹을 수 있어 그때는 `SET LOCAL`로 바꿔야 합니다.
- 다른 도구(`qa_seed`의 PG 적재 등)는 아직 동기입니다. dev 도구라 그대로 뒀습니다.

## 그래프: 전사 두 단계 (`notree/graphs/qa/graph.py`)

| 단계 | 하는 일 |
|---|---|
| `search_transcript` | 노트 결과의 강의별 최고 점수로 `PRIORITY_LECTURES`(2)개 강의를 골라 그 전사만. 노트 결과에 강의 정보가 없으면 과목 전체 (예전과 같음) |
| `search_transcript_all` (새로) | 과목 전체 전사 |

| 판단 | 처리 |
|---|---|
| 우선 강의 전사 최고 점수 < `EXPAND_MIN`(0.3) | 답하기 전에 바로 과목 전체 |
| 0.3 이상(충분 0.6 미만) | 웹으로 가지 않고 먼저 답함. LLM이 "근거 더 필요"면 남은 시간·LLM 호출 예산 안에서 과목 전체 → 웹 |
| 최종 답변 가능 여부 | 점수가 아니라 LLM이 판단 (정확성 보장은 아님) |

- 근거 선택(`evidence`)은 점수순 유지 + **같은 ID는 한 번만**(단계마다 다시 찾은 경우). 검색 단계의 순서는 근거 선택에서 유지되지 않으며, 이 조합을 `qa_pg_eval`로 함께 잽니다.
- 근거에 `lecture_id`가 붙습니다 (`Hit`, `QaHit`). `Retriever.search`에 선택 인자 `lecture_ids` — 그래프는 범위가 있을 때만 넘깁니다.

## 새 질문 세트 평가 (2026-10-18)

`notree.dev.qa_fresh_eval` — 새 질문 30개(AI가 강의 6개로 만든 추가 초안, 기준값을 정할 때 쓰지 않은 질문)와 별도 정답표로 검색과 실제 답변을 함께 봅니다. 질문·정답표·강의 원문은 `data/fresh/`(저장소 밖).

- 정답표는 답변 생성이 끝난 뒤 채점에만 읽습니다. 가짜 OpenAI 클라이언트로 돌려 프롬프트에 정답표에만 있는 문구가 없음을 확인했습니다.
- 자동 채점: 기대 상태 일치, 정답 항목별 근거 ID가 LLM에 전달·인용됐는지. 정답표 근거 ID는 비완전한 초안이고 다른 구간도 인정하므로 **하한**입니다. 요약 노트 `s{n}`은 같은 구간 전사 `t{n}`과 같은 근거로 셉니다.
- 의미 채점: 채점표(질문·정답 항목·채점 주의·답변 문장별 인용·인용 원문)로 항목마다 충족/일부/누락, 인용이 주장을 뒷받침하는지, 자료에 없는 내용을 지어냈는지 봅니다. 답변 모델(gpt-4o-mini)과 다른 채점자가 봅니다.
- `--limits 3,5`: 출처마다 검색 상한. 노트에서 멈출 때 전달 근거 3개·5개를 같은 질문으로 비교 (품질·토큰·지연).
- 키 없이(`--llm fake`, 단어 추출 검색어) 돌리면 근거 일치가 20%뿐입니다. 이번 질문은 강의 용어를 피해 바꿔 말한 질문("외운 문제" ↔ overfitting)이라 질문 문장의 단어로는 못 찾습니다 → 실제 LLM 검색어로 재야 의미가 있습니다.

## 깨지는 변경

| 무엇 | 이전 | 이후 |

| 의존성 | — | `psycopg[binary]` |

## 남은 것

- 팀원 질문 평가에 **실제 답변**도 포함 (지금 `qa_pg_eval`의 답변기는 가짜 accept·oracle): 질문 각 부분을 다뤘는지, 인용 원문이 주장을 뒷받침하는지, 노트에서 멈췄을 때 조건·예외가 빠지는지, 자료에 없는 질문에 억지로 답하지 않는지. "첫 전달 근거 32/33"은 정답 구간 하나가 들어갔다는 뜻이지 복합 질문의 모든 부분이 갖춰졌다는 뜻은 아님
- 팀원이 쓴 질문으로 기준값(0.3·0.6·강의 2개) 검증. 지금 질문은 본문 단어를 빌려 써서 쉬울 수 있음
- 노트에서 멈출 때 전달 근거가 3개뿐 — 바로 늘리지 않고, 같은 질문으로 3개·5개를 답변 품질·토큰·지연으로 비교해 결정
- 검색어 문제(ml13: "예측값" vs 강의의 "h", "로그 0") — 검색어 확장·동의어
- trgm 인덱스 후보 축소와 정답 손실 비교, 실제 규모 지연
- 질문·과목 행까지 PG로 (지금은 SQLite 작업 DB)
