# pgvector 통합 결정 (2026-10-20)

근거: [측정 기록 2026-10-19](../measurements/2026-10-19-vector-compare/README.md) · 아래 pgvector 점검. **이 문서는 결정 기록이며 코드는 바꾸지 않는다.**
기본 검색을 벡터로 바꿀지는 통합 경로의 답변 품질 평가 뒤에 정한다.

## 바뀌는 범위

worker 구조(Redis Streams · 실행권 · 재시도 · ACK)와 대화 메모리는 그대로 쓴다. 바뀌는 곳은 Q&A 근거 검색과 문서 색인 경로뿐이다.
Redis는 벡터를 저장하지 않는다. pgvector는 PostgreSQL 확장이라 별도 벡터 DB를 두지 않는다.

| 부분 | 변경 |
|---|---|
| PostgreSQL | 노트 · 전사에 대응하는 임베딩 저장 (문서 버전과 함께) |
| 문서 저장 경로 | 문서 생성 · 수정과 같은 트랜잭션에 "이 버전의 임베딩 필요" 의도 등록 → outbox → batch |
| `qa_search` | pg_trgm 옆에 pgvector 검색 어댑터 추가 |
| Q&A 그래프 | 검색 방식별 설정 분리 (아래 D4) |
| 권한 · 삭제 | 검색 시 사용자 · 과목 · 문서 상태 · 버전 확인 |

## 결정

**D1. 최신 문서 공백** — 방금 생성 · 수정된 문서는 임베딩이 아직 없을 수 있다. "벡터 실패 시 trgm"만으로는 메워지지 않는다.
- 현재 버전의 임베딩이 있는 문서는 벡터로, 임베딩이 없거나 본문보다 오래된 문서는 pg_trgm으로 찾는다
- 두 결과에 후보 자리를 **각각 배정**하고 같은 문서는 중복 제거한다. 단순히 뒤에 붙인 뒤 상위 k개로 자르면 최신 문서가 다시 탈락하므로, 모델에 전달하는 자리도 확보한다
- 수정 전 임베딩으로 찾은 문서를 최신 본문의 근거로 쓰지 않는다 (버전 불일치면 벡터 후보에서 제외)
- 한계: 최신 문서에 질문의 표현이 없으면 trgm도 못 찾는다. "방금 말한 내용"용으로 **최근 전사 구간을 시간 기준으로 가져오는 후보**를 따로 평가한다

**D2. 임베딩 작업과 batch** — 조각마다 작업을 만들지 않는다.
- 강의별로 변경을 누적해 일정 간격으로 묶어 임베딩하고, 처리 중 추가된 변경은 다음 묶음으로 (실시간 요약의 요청 합치기와 같은 방식)
- 묶음 하나의 문서 수 · 토큰 수 제한, 작은 묶음마다 슬롯 반환
- 최종 노트 · 과목 노트와의 배정 우선순위를 명시
- 색인 지연(문서 저장 → 벡터 저장)을 측정한다. 우선 기존 batch를 쓰고, 다른 작업을 실제로 지연시키면 임베딩용 실행 용량을 분리한다
- 벡터 저장 시 업무 서비스가 "지금도 같은 문서 버전인지" 확인한다 (늦게 끝난 임베딩이 최신 버전을 덮지 않음)

**D3. 질문 재작성과 지연** — 대화 맥락을 해석한 질문을 임베딩하므로 순서는 `질문 재작성 → 질문 임베딩 → 검색`이다. 두 호출은 병렬로 돌릴 수 없다.
LLM 검색어 생성 911ms · 질문 임베딩 148ms는 서로 다른 측정의 참고값이라 합산하지 않고, 통합 경로에서 다시 잰다.

**D4. 0.3 · 0.6 기준** — 지금 값은 trgm 점수 전용이다. 벡터 점수에 그대로 쓰지 않는다.
- 검색 방식별 설정을 분리한다
- 범위 밖 질문과 정답 근거의 벡터 점수가 겹쳤으므로(측정 기록 3장) 점수 하나로 답변 가능 여부를 정하지 않는다. 초기에는 상위 k개를 후보로 넘기고, 질문의 각 부분에 근거가 있는지는 답변 단계에서 판단한다
- 지금 인용 검증은 "받은 근거의 ID인지"만 확인한다. 근거가 주장을 실제로 뒷받침하는지(내용 검증)는 보장하지 않고, LLM의 `needs_more_evidence`도 모델 판단이다. 답변 평가에서 누락 · 잘못된 근거 사용을 따로 확인한다

**D5. 실패 대비와 결합** — 질문 임베딩 실패 시 그 질문은 pg_trgm으로 처리한다. 두 검색을 항상 RRF로 합치지 않는다 (동일 비중 RRF는 벡터 단독보다 낮았음). D1의 자리 배정은 RRF가 아니라 색인 상태에 따른 분리다.

**D6. 색인 방식** — 첫 통합은 정확 검색. HNSW는 데이터 증가 · 부하 측정 뒤 판단한다.

## 구현 순서 — 통합 기준부터

pgvector 작업은 오래된 `feat/qa-pg-search` 위에서 시작하지 않는다. 최신 main에 필요한 변경을 먼저 통합 · 검증한 기준에서 새 브랜치를 만든다.

로컬에서 main(`a8995e4`)에 차례로 시험 병합한 결과 (푸시하지 않음):

| 순서 | 브랜치 | main 대비 | 충돌 |
|---|---|---|---|
| 1 | `feat/redis-liveness-default` (`fix/review-6` 포함) | 8커밋 앞 · 3커밋 뒤 | CHANGELOG만 |
| 2 | `feat/qa-conversation-memory` | 4커밋 앞 · 0 뒤 | 없음 |
| 3 | `feat/qa-pg-search` | 11커밋 앞 · 36커밋 뒤 | CHANGELOG · README · `graphs/qa/graph.py` · `mcp_server/server.py` |

1 · 2는 단독으로는 병합이 쉽다. 3은 대화 메모리 · 실행 시작 절차 변경과 Q&A 그래프 · MCP 서버에서 겹치므로 직접 맞춰야 한다.
권장 순서: **① liveness 머지 → ② 대화 메모리 머지 → ③ PG 검색을 최신 main에 맞춰 통합(충돌 해결 + 전체 시험 + PG 시험) → ④ 그 기준에서 pgvector 브랜치**.
평가 도구(`exp/vector-compare`)는 ③ 뒤에 PG 검색 의존성을 확인하고 따로 합친다.
