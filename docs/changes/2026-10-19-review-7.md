## ① 복구 스캔 도중 Redis 재시작 (P1)

문제: `recover_after_redis_loss`는 시작할 때 유실 여부를 보고, **끝에서 run_id를 다시 읽어** 표시 키에 썼다. 스캔 도중 Redis가
재시작하면 복구하지 않은 새 Redis에 새 run_id로 "확인함" 표시 → 다음 스캔 재전송 0건, 메시지 없음, 작업은 running으로 멈춤.

고친 뒤: 표시 키에는 스캔을 **시작할 때** 본 run_id를 쓴다. 도중에 재시작했다면 그 쓰기는 새 Redis에 들어가지만 값이 새 run_id와
달라서 다음 주기에 유실로 잡히고, 전달 세대를 다시 올려 처음부터 복구한다. 비교·쓰기 사이의 경쟁도 같은 이유로 안전하다
(어느 Redis에 써지든 값은 시작 때의 run_id).

`INFO`를 못 쓰는 Redis에서는 scheduler 시작 때 경고를 남긴다 (스냅숏 복원·재시작 도중 유실을 못 잡음). 운영 조건:
INFO 허용 + 비영속(`save ""`, `appendonly no`).

시험(실제 redis-server): 스캔 중 `job_recover_orphans` 응답 직후 Redis 재시작 → 이번 스캔 0건, Stream 비어 있음 → 다음 스캔 1건 재전송
→ worker가 done. 고치기 전 코드는 다음 스캔도 0건.

## ② 저장 확인 실패를 '미저장'으로 오인 · ④ 요약 저장 응답 전부 유실 (P2)

문제: 6차 ③의 worker 쪽 `done_check`는 확인이 오류·시간 초과로 끝나면 `saved=False`로 보고 실패를 확정했다 (확인 불가 ≠ 미저장).
실시간 요약은 `done_check`가 없어서 저장 응답 4번을 모두 잃으면 요약 [1–2]는 저장됐는데 작업은 failed.

고친 뒤 — **결과 존재 여부와 최종 상태를 서버가 한 트랜잭션에서 정한다**:
- `job_fail`이 같은 트랜잭션에서 이 작업의 결과가 저장됐는지 본다(`_result_saved`: Q&A는 질문이 answered이고 저장한 idem_key가
  이 작업, 실시간 요약은 `summaries.idem_key = job_id`). 저장돼 있으면 실패 대신 done으로 확정하고 `done_instead=true`를 돌려준다.
  ⚠️ 계약 `JobFailOut.done_instead` 추가. worker는 `failed` 또는 `done_instead`를 확인한 뒤에만 XACK.
- Redis 유실 복구(`job_recover_orphans`)가 마감·시도 한도로 실패 확정할 때도 같은 확인 → `done_instead` 목록 (계약 추가).
- worker 쪽 `done_check`(6차 ③)는 없앴다. 확인 경로가 둘이면 서로 다른 답을 낼 수 있다.
- **확인 불가**(`job_fail` 응답을 끝내 못 받음): 실패를 확정하지 않고 ACK도 안 한다 → 재배송된다. 재배송이 **시도 > 한도**면 핸들러
  (LLM)를 실행하지 않고 `job_fail`만 다시 보낸다 → 서버가 결과 유무로 실패·완료를 정한다.
- 동작 변화: 마지막 시도 중에 worker가 죽어 재배송된 작업도 이제 핸들러를 다시 돌리지 않고 확정만 한다 (전에는 한도를 넘겨 한 번 더
  실행됐다). 결과가 저장돼 있으면 완료, 없으면 실패(사용자는 다시 시도 가능). 실시간 요약(총 1회)은 실패한 구간을 다음 요약이 처리하는
  기존 정책 그대로.
- 남는 경계: 요약 저장이 `stale`(다른 요약이 이미 그 위치를 넘김)로 끝난 작업은 저장 행이 없어서, 그 응답까지 모두 잃으면 실패로
  남는다. 요약 내용은 다른 요약이 덮었으므로 데이터 손실은 없다.

시험 (고치기 전 코드에서 앞의 둘은 failed):
| 시험 | 결과 |
|---|---|
| Q&A 시도 한도 1: 저장 응답 유실 + `job_fail` 첫 확인 묶음(3번)도 전달 실패 | 그동안 running(실패 확정 안 함) → 재배송은 확정만 → done, 시도 2, LLM·저장 1번 |
| 요약: `summary_publish` 응답 4번 모두 유실 | done, 요약 [1–2], LLM 1번 |
| Redis 유실 복구: 한도 다 쓴 running 둘 (하나만 요약 저장됨) | 저장된 쪽 done, 아닌 쪽 failed |
| 6차 시험 (마지막 시도 응답 유실 / 저장 직후 마감 / 저장 전 끊김) | 그대로 통과 (done / done / failed) |

## ③ 기본 DB 모드의 `touch()` 무기한 대기 (P2)

문제: 6차 ⑤에서 MCP heartbeat에 시간 제한을 넣었지만, 그 뒤의 Redis `touch()`(메시지 방치 시간 초기화)는 제한 없이 기다렸다.
여기가 멈추면 다음 DB heartbeat와 만료 판단도 멈춰, worker는 계속 실행하는데 DB lease는 서버에서 만료된다.

고친 뒤: `touch()`는 heartbeat 주기만큼만 기다리고, 넘기면 이번 박동만 건너뛴다 → heartbeat 루프는 계속.

시험(무응답 주입): touch가 멈춰도 0.4초 동안 DB heartbeat 4번 이상, lease 유지 / touch가 멈춘 상태에서 heartbeat도 멈추면
0.4초 안에 LeaseLost. 고치기 전 코드는 둘 다 실패.
