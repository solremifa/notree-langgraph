# 2026-10-16 변경 정리: 레인 분리 (Q&A가 실시간 요약에 밀리지 않게)

브랜치 `feat/lanes`. 아키텍처 검토 문서의 PostgreSQL 실측에서 나온 1순위 문제를 고칩니다.

## 왜

실측(PostgreSQL 16, 2 vCPU, 사용자 50~800명)에서 DB는 800명에도 CPU 22%였지만, **Q&A 완료까지 시간이 56초**까지 늘었습니다.
원인은 Q&A·채점·실시간 요약이 모두 같은 `notree:rt` Stream에 있어서, 계속 생기는 요약 뒤에 Q&A가 줄을 섰기 때문입니다.
Q&A 전용 슬롯을 두었을 때 800명에서도 4.1초(혼자 쓸 때와 같음)였습니다.

## 바뀐 것

| 레인 | Stream | 작업 | 기본 설정 |
|---|---|---|---|
| `qa` (새로) | `notree:qa` | `qa`, `grading` | lease 15초 · 재배송 20초 · 2회 · 제한 90초 · 동시 4 |
| `rt` | `notree:rt` | `live_summary` | 그대로 |
| `batch` | `notree:batch` | `final_note`, `course_update` | 그대로 |

- 작업 종류 → Stream 연결은 MCP 서버의 `STREAM_OF`. 배정기는 의도에 기록된 Stream으로 보내므로 코드 변경 없음.
- `qa` 레인 permit 유효 시간은 rt와 같은 값(`NOTREE_PERMIT_TTL_RT`, 기본 5분).
- worker 프로세스를 하나 더 띄웁니다: `uv run python -m notree.worker --stream qa --name A`.

### 빌려 쓰기 (선택)

`qa` worker는 자기 대기열이 비었을 때 `rt` 작업을 가져와 쓸 수 있습니다.

```
uv run python -m notree.worker --stream qa --concurrency 16 --borrow-slots 8
# 또는 NOTREE_QA_BORROW_SLOTS=8
```

- 자기 Stream에 회수할 것도 새것도 없을 때만 빌립니다. 자기 레인이 언제나 먼저입니다.
- 빌린 작업은 동시에 `borrow_slots`개까지만 → 나머지 슬롯(위 예에서 8개)은 언제나 Q&A 몫으로 비어 있습니다.
  `borrow_slots`는 동시 수 - 1을 넘지 못합니다.
- 빌린 작업의 lease·재배송·시도 한도·ACK는 원래 레인(rt) 설정을 따릅니다.
- 기본값은 0(고정). 아래 측정을 보고 팀에서 정합니다.

## 측정: 한 대기열 vs 고정 vs 빌려 쓰기

`notree/dev/lane_bench.py`. 실제 worker 코드와 실제 Redis 7, DB는 가짜(큐·슬롯 정책만 봄).
슬롯 합계 64, Q&A 16슬롯(빌려 쓰기 8), 요약 6초·Q&A 4초(±30%), Q&A 초당 2개, 300초(10배 빠르게 돌림, 앞 20% 제외).

| 요약 도착 | 설계 | Q&A 대기 p50 / p95 | 요약 대기 p50 / p95 | 요약 처리/s |
|---|---|---|---|---|
| 6/s (여유) | 한 대기열 | 0 / 0 | 0 / 0 | 5.4 |
| | 고정 | 0 / 0 | 0 / 0 | 5.3 |
| | 빌려 쓰기 8 | 0 / 0 | 0 / 0 | 5.7 |
| 9/s (거의 꽉 참) | 한 대기열 | 0 / 1.4초 | 0 / 1.5초 | 8.4 |
| | 고정 | 0 / 0 | **1.7 / 4.0초** | 7.9 |
| | 빌려 쓰기 8 | 0 / 0.7초 | 0 / 0.7초 | 8.0 |
| 12/s (넘침) | 한 대기열 | **18.2 / 33.0초** | 19.0 / 33.0초 | 9.2 |
| | 고정 | 0 / 0 | **50.0 / 73.9초** | 7.2 |
| | 빌려 쓰기 8 | 0.1 / 1.4초 | 31.5 / 47.5초 | 8.7 |

빌려 쓰는 수만 바꿔 본 것 (요약 9/s): 4개 → Q&A p95 0.1초·요약 p95 2.9초, 8개 → 0.7초·0.7초, 12개 → 0.6초·0.4초.

- **한 대기열**은 넘치는 순간 Q&A도 같이 밀립니다 (지금 구조).
- **고정**은 Q&A를 완벽히 지키지만, Q&A가 한가할 때 16슬롯이 놀아서 요약이 먼저 밀립니다.
- **빌려 쓰기**는 Q&A 대기를 1.4초 안으로 지키면서 요약 쪽 손해를 대부분 되찾습니다.
  Q&A가 몰릴 때 빌린 요약이 끝날 때까지 남는 슬롯이 Q&A 몫(8개)뿐이라 p95가 조금 늘어난 것입니다.
- 넘칠 때(12/s) 요약 대기는 어느 설계든 계속 늘어납니다. 이건 레인으로 못 고치고 요약 간격 조절(대책 ②)이나 LLM 처리량을 늘려야 합니다.

**권장**: 빌려 쓰기, Q&A 슬롯의 절반(16 중 8). 팀이 Q&A 대기를 "항상 0"으로 지켜야 한다고 보면 고정.

한계: DB·MCP 지연은 빼고 큐 정책만 봤습니다. 요약·Q&A 시간은 고정 분포로 흉내 냈습니다.

## 깨지는 변경

| 무엇 | 이전 | 이후 |
|---|---|---|
| `qa`, `grading` 작업의 Stream | `notree:rt` | `notree:qa` → **qa worker를 띄워야 처리됨** |
| `Worker._ack`, `_touch`, `process` | Stream을 `self.cfg`에서 | 메시지가 온 레인의 설정(`cfg`)을 인자로 받음 |
