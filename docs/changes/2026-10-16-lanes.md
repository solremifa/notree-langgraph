# 2026-10-16 변경 정리: 레인 분리 (Q&A가 실시간 요약에 밀리지 않게)

브랜치 `feat/lanes`. 아키텍처 검토 문서의 PostgreSQL 실측에서 나온 1순위 문제를 고칩니다.

## 왜

실측(PostgreSQL 16, 2 vCPU, 사용자 50~800명)에서 DB는 800명에도 CPU 22%였지만, **Q&A 완료까지 시간이 56초**까지 늘었습니다.
원인은 Q&A·채점·실시간 요약이 모두 같은 `notree:rt` Stream에 있어서, 계속 생기는 요약 뒤에 Q&A가 줄을 섰기 때문입니다.
Q&A 전용 슬롯을 두었을 때 800명에서도 4.1초(혼자 쓸 때와 같음)였습니다.

## 바뀐 것

| 레인 | Stream | 작업 | 기본 설정 |
|---|---|---|---|
| `qa` (새로) | `notree:qa` | `qa`, `grading` | lease 15초 · 재배송 20초 · 2회 · 제한 90초 · 동시 4 |
| `rt` | `notree:rt` | `live_summary` | 그대로 |
| `batch` | `notree:batch` | `final_note`, `course_update` | 그대로 |

- 작업 종류 → Stream 연결은 MCP 서버의 `STREAM_OF`. 배정기는 의도에 기록된 Stream으로 보내므로 코드 변경 없음.
- `qa` 레인 permit 유효 시간은 rt와 같은 값(`NOTREE_PERMIT_TTL_RT`, 기본 5분).
- worker 프로세스를 하나 더 띄웁니다: `uv run python -m notree.worker --stream qa --name A`.

### 빌려 쓰기 (선택)

`qa` worker는 자기 대기열이 비었을 때 `rt` 작업을 가져와 쓸 수 있습니다.

```
uv run python -m notree.worker --stream qa --concurrency 16 --borrow-slots 8
# 또는 NOTREE_QA_BORROW_SLOTS=8
```

- 자기 Stream에 회수할 것도 새것도 없을 때만 빌립니다. 자기 레인이 언제나 먼저입니다.
- 빌린 작업은 동시에 `borrow_slots`개까지만 → 나머지 슬롯(위 예에서 8개)은 언제나 Q&A 몫으로 비어 있습니다.
  `borrow_slots`는 동시 수 - 1을 넘지 못합니다.
- 빌린 작업의 lease·재배송·시도 한도·ACK는 원래 레인(rt) 설정을 따릅니다.
- 기본값은 0(고정). 아래 측정을 보고 팀에서 정합니다.

## 측정: 한 대기열 vs 고정 vs 빌려 쓰기

`notree/dev/lane_bench.py`. 실제 worker·배정기 코드와 실제 Redis 7, DB는 가짜(큐·슬롯·배정 정책만 봄).
슬롯 합계 64, Q&A 16슬롯(빌려 쓰기 8), 요약 6초·Q&A 4초(±30%), Q&A 초당 2개, 300초(10배 빠르게 돌림, 앞 20% 제외).
시드 3개로 돌린 중앙값, 괄호는 최소~최대. **리뷰 반영 후 다시 잰 값**입니다 (처음 수치는 집계 오류로 폐기, 아래 "리뷰 반영" 참고).

대기 = 등록 → 시작. 끝까지 시작 못 한 작업은 (측정 종료 - 등록)으로 넣은 하한값. 처리량 = 측정 구간 안에서 끝난 작업만.

| 요약 도착 | 설계 | Q&A 대기 p50 / p95 | 요약 대기 p50 / p95 | 요약 처리/s | 종료 때 남은 요약 |
|---|---|---|---|---|---|
| 9/s (거의 꽉 참) | 한 대기열 | 0 / 0.3초 | 0 / 0.3초 | 8.1 | 0 |
| | 고정 | 0 / 0 | **3.1 / 7.0초** | 7.9 | 47 (35~76) |
| | 빌려 쓰기 8 | 0 / 0.9초 | 0 / 0.9초 | 8.1 | 0 |
| 12/s (넘침) | 한 대기열 | **18.0 / 29.2초** | 19.0 / 29.2초 | 9.4 | 305 |
| | 고정 | 0 / 0 | **44.4 / 69.7초** | 8.0 | 756 |
| | 빌려 쓰기 8 | 0 / 1.2초 | 19.1 / 37.7초 | 9.2 | 401 |

빌려 쓰는 수만 바꿔 본 것 (요약 9/s, Q&A p95 / 요약 p95): 4개 0.6초 / 1.4초, 8개 0.9초 / 0.9초, 12개 1.1초 / 0.5초.

**배정 단계까지 포함** (요약 9/s, 빌려 쓰기 8, 측정 시작 때 요약 의도 2,000개가 대기 중):

| 배정 | Q&A 대기 p50 / p95 / 최대 | 요약 대기 p50 |
|---|---|---|
| 레인 구분 없음 (이전 배정기) | **55.1 / 105.6 / 108.9초** | 115.2초 |
| 레인별 몫 (이번 수정) | 0.5 / 1.8 / 2.6초 | 113.9초 |

- **한 대기열**은 넘치는 순간 Q&A도 같이 밀립니다 (지금 main).
- **고정**은 Q&A를 완벽히 지키지만, Q&A가 한가할 때 16슬롯이 놀아서 요약이 먼저 밀리고 처리량도 가장 낮습니다.
- **빌려 쓰기**는 Q&A 대기를 p95 1.2초 안으로 지키면서 요약 처리량을 한 대기열과 거의 같게 되찾습니다.
- **배정 단계**를 레인별로 바꾸지 않으면 Redis 뒤를 나눠도 Q&A가 100초 넘게 밀립니다 (리뷰 지적 재현).
  남은 0.5초는 배정기 주기(0.5초)를 기다리는 시간입니다. API가 커밋 직후 바로 XADD하는 구조(`feat/redis-state`)면 없어집니다.
- 넘칠 때 요약 대기는 어느 설계든 계속 늘어납니다. 레인으로 못 고치고 요약 간격 조절이나 LLM 처리량으로 풀어야 합니다.

**권장**: 빌려 쓰기, Q&A 슬롯의 절반(16 중 8). Q&A 대기를 "항상 0"으로 지켜야 한다면 고정.

한계: DB·MCP 지연은 빼고 큐·배정 정책만 봤습니다. 요약·Q&A 시간은 고정 분포로 흉내 냈고, 부하 생성기와 worker가 한 프로세스에서 돕니다.

## 리뷰 반영 (같은 날)

`3d12a54` 검토에서 나온 두 가지를 고쳤습니다.

| # | 문제 | 고친 방법 | 확인 |
|---|---|---|---|
| 1 | 배정기가 모든 레인을 생성 순서로 0.5초마다 10개씩 골라, 요약 2,000개 뒤의 Q&A가 201번째 묶음(약 100초)에 나감 | `job_reserve_pending`에 `stream`(레인) 인자 추가 — DB는 "이 레인의 대기 의도를 생성 순서로 N개"만. 배정기가 바퀴마다 qa → rt → batch 순으로 레인별 몫(10/10/5)을 고르고, 몫을 다 채운 레인이 있으면 쉬지 않고 다음 바퀴 (한 주기 최대 200개) | `test_allocator_does_not_queue_qa_behind_summary_backlog`(1초 안), `test_mixed_allocator_shows_the_old_delay`, `test_allocator_quota_per_round`, 위 "배정 단계까지 포함" 표 |
| 2 | 벤치마크가 측정 종료 뒤 마저 끝난 작업까지 처리량에 넣고 분모는 측정 구간만 씀 (0.2초 구간에서 완료 0개인데 6.2개/초로 보고) | 처리량은 구간 안에서 끝난 작업만. 대기는 시작 못 한 작업을 하한값으로 포함, 종료 때 남은 대기열 수를 같이 보고. 시드 고정(`--seed`) | 같은 0.2초 구간 재현 → 0개/초. 위 표는 모두 다시 잰 값 |

- 배정 정책(레인 순서·몫·주기 상한)은 `settings.ALLOC_LANES`, `ALLOC_MAX_PER_TICK`, `ALLOC_INTERVAL_SEC`, 환경변수 `NOTREE_ALLOC_QA/_RT/_BATCH`.
- `jobs(state, stream, created)` 인덱스 추가 (레인별 조회용).
- 레인 구분 없이 고르는 방식은 `run_allocator(..., lanes=())`로 남겨 비교에 씁니다.

## 깨지는 변경

| 무엇 | 이전 | 이후 |
|---|---|---|
| `qa`, `grading` 작업의 Stream | `notree:rt` | `notree:qa` → **qa worker를 띄워야 처리됨** |
| `Worker._ack`, `_touch`, `process` | Stream을 `self.cfg`에서 | 메시지가 온 레인의 설정(`cfg`)을 인자로 받음 |
| 배정기 | 모든 레인을 생성 순서로 10개씩 | 레인별 몫으로 (`job_reserve_pending`에 `stream`, 선택 인자라 이전 호출도 동작) |
