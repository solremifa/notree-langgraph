# 2026-10-18 변경 정리: 실시간 요약 범위 합치기 (`feat/summary-coalesce`, PoC)

설계 v0.2 검토의 ③(후속 요약 등록·동시 요청·누락 복구)을 구현했습니다. 실시간 요약은 지금까지 미구현이었고, 이번에 PoC 경로(SQLite, 가짜 LLM)를 만들었습니다.

## 규칙

| 무엇 | 어떻게 | 어디서 |
|---|---|---|
| 판단 기준 | Redis가 아니라 DB의 강의 위치 세 개: `saved_until` ≥ `attempted_until` ≥ `processed_until` | `lectures` |
| 강의당 대기 요약 1개 | 유일 부분 인덱스 `jobs(lecture_id) WHERE kind='live_summary' AND state='pending'`. 커밋이 넣다가 충돌하면 "합쳐짐" | DB 제약 |
| 강의당 동시 실행 1개 | 같은 강의 요약이 reserved·sent·running이면 대기 요약을 허가하지 않음 | `job_reserve_pending` (서비스) |
| 합치기 | 대기 요약은 시작할 때(`transcript_range`) 요약 위치 이후 전사를 모두 읽음 | |
| 저장 | 요약 + 위치 이동을 한 트랜잭션. 멱등(idem_key), 실행권(permit), 세대, `from_seq = processed_until + 1`일 때만 (위치는 앞으로만) | `summary_publish` |
| 녹음 종료 | `ended`, 세대 +1 → 진행 중이던 요약 저장은 `generation_mismatch` | `lecture_end` |
| 누락 복구 | 녹음 중 · 요약 안 된 전사 있음 · **아무도 읽어 가지 않은 전사 있음** · 대기·실행 중 요약 없음 → 1건 | `summary_recover` (scheduler 주기) |

"후속 1건은 결과 저장 트랜잭션에서 등록"이라던 검토 때의 제안 대신, **커밋이 대기 1건을 등록하고 배정이 앞 요약 끝날 때까지 기다리는** 방식으로 바꿨습니다.
- 후속 요청이 커밋 시점에 DB에 남으므로, 요약 저장과 등록 사이에서 잃어버릴 구간이 없습니다.
- 요약 저장 트랜잭션은 자기 작업이 아직 running인 상태라 "대기 1개" 제약과 부딪혔습니다.

실패한 요약 구간은 복구 스캔이 혼자 다시 등록하지 않습니다(`attempted_until` 조건). 새 전사가 오면 커밋이 등록하고, 그 요약이 처리 위치부터 읽으므로 실패 구간까지 함께 처리합니다.

## 새 도구 (계약: `notree/contracts/tools.py`, 모두 [PoC])

`lecture_start` · `transcript_commit` · `lecture_end` · `lecture_get`(dev) · `summary_recover`(scheduler).
계획 상태였던 `transcript_range`·`summary_publish`를 구현하면서 `from_seq`, `state`, `status`(published·duplicate·stale) 필드를 더했습니다.

시험하면서 본 것: 앞 요약이 배정만 되고 아직 전사를 읽기 전에 커밋이 오면 대기 1건이 더 생기고, 앞 요약이 그 전사까지 읽어 가면 뒤 요약은 **LLM을 부르지 않고** 빈 실행으로 끝납니다. 구간은 겹치지 않습니다. 비용은 작업 하나의 배정·DB 읽기뿐이라 그대로 두었습니다.

## 하지 않은 것

- 요약 주기 조절(20·40·60초)과 "확정 전사 100자 이상·20초 대기" 같은 실행 조건 — 지금은 대기 요약이 허가되는 즉시 실행
- 실제 OpenAI 요약, 화면 알림(outbox), 녹음 종료 때 최종 노트 등록
- 비용 한도 검사 (복구 스캔에 넣을 자리만 표시)
- PG로 옮기기 (같은 제약·조건을 PG 부분 유일 인덱스로)
