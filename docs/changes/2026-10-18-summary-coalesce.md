# 2026-10-18 변경 정리: 실시간 요약 범위 합치기 (`feat/summary-coalesce`, PoC)

설계 v0.2 검토의 ③(후속 요약 등록·동시 요청·누락 복구)을 구현했습니다. 실시간 요약은 지금까지 미구현이었고, 이번에 PoC 경로(SQLite, 가짜 LLM)를 만들었습니다.

## 규칙

| 무엇 | 어떻게 | 어디서 |
|---|---|---|
| 판단 기준 | Redis가 아니라 DB의 강의 위치 세 개: `saved_until` ≥ `attempted_until` ≥ `processed_until` | `lectures` |
| 강의당 대기 요약 1개 | 유일 부분 인덱스 `jobs(lecture_id) WHERE kind='live_summary' AND state='pending'`. 커밋이 넣다가 충돌하면 "합쳐짐" | DB 제약 |
| 강의당 동시 실행 1개 | 같은 강의 요약이 reserved·sent·running이면 대기 요약을 허가하지 않음 | `job_reserve_pending` (서비스) |
| 합치기 | 대기 요약은 시작할 때(`transcript_range`) 요약 위치 이후 전사를 모두 읽음 | |
| 저장 | 요약 + 위치 이동을 한 트랜잭션. 멱등(idem_key), 실행권(permit), 세대, `from_seq = processed_until + 1`일 때만 (위치는 앞으로만) | `summary_publish` |
| 녹음 종료 | `ended`, 세대 +1 → 진행 중이던 요약 저장은 `generation_mismatch` | `lecture_end` |
| 누락 복구 | 녹음 중 · 요약 안 된 전사 있음 · **아무도 읽어 가지 않은 전사 있음** · 대기·실행 중 요약 없음 → 1건 | `summary_recover` (scheduler 주기) |

"후속 1건은 결과 저장 트랜잭션에서 등록"이라던 검토 때의 제안 대신, **커밋이 대기 1건을 등록하고 배정이 앞 요약 끝날 때까지 기다리는** 방식으로 바꿨습니다.
후속 요청이 전사 커밋 시점에 DB에 확실히 남으므로, 요약 저장과 후속 등록 사이에서 잃어버릴 구간이 없습니다.

실패한 요약 구간은 복구 스캔이 혼자 다시 등록하지 않습니다(`attempted_until` 조건). 새 전사가 오면 커밋이 등록하고, 그 요약이 처리 위치부터 읽으므로 실패 구간까지 함께 처리합니다.

## 새 도구 (계약: `notree/contracts/tools.py`, 모두 [PoC])

`lecture_start` · `transcript_commit` · `lecture_end` · `lecture_get`(dev) · `summary_recover`(scheduler).
계획 상태였던 `transcript_range`·`summary_publish`를 구현하면서 `from_seq`, `state`, `status`(published·duplicate·stale) 필드를 더했습니다.

## 리뷰 반영 (3b1c00e 이후)

세 문제를 시험으로 먼저 재현한 뒤 고쳤습니다.

| 문제 | 고치기 전 | 고친 뒤 |
|---|---|---|
| P1 다른 작업의 permit으로 남의 강의 요약 변경 | Alice의 Q&A·echo 작업 permit(유효)으로 Bob 강의에 `summary_publish` → published, Bob의 요약·위치가 바뀜 | 저장 트랜잭션에서 **작업 종류 live_summary · 작업의 lecture_id = 대상 · 작업 사용자 = 강의 주인 · 현재 실행권** 확인. duplicate 경로도 작업↔강의 연결과 저장된 결과의 강의를 확인 |
| P1 같은 묶음 재전송이 실패한 요약을 다시 등록 | 커밋이 새 번호와 관계없이 `saved > processed`면 등록 → 재전송만으로 실패 구간 LLM 반복 | **새 전사가 실제로 저장됐을 때만** 등록. 재전송·빈 묶음은 상태만 돌려줌 (`added=0`) |
| P2 실행권을 잃은 worker가 attempted_until 변경 | 이전 permit으로 `transcript_range` 성공, 복구 판단 값이 올라감 | 같은 작업↔강의 연결 + **현재 실행권** 확인 뒤에만 변경. 계약에 상태 변경 도구(write)로 표시 |

## 리뷰 2차 반영

| 문제 | 고친 뒤 |
|---|---|
| 사용자 재시도가 "강의당 대기 1개" 제약과 충돌 (`UNIQUE constraint failed`) | 후속 요약이 대기·실행 중이면 되살리지 않고 "후속 요약이 실패 구간부터 함께 처리"를 돌려줌. 녹음이 끝났으면 되살리지 않음. 다른 요약이 없을 때만 되살림 |
| 저장 응답만 유실 → 요약은 저장, 작업은 failed | LLM 재실행과 저장 확인을 구분: 같은 시도 안에서 같은 idem_key로 저장을 다시 보냄(멱등 → duplicate). 작업이 다시 실행돼도 `already_published`면 요약 없이 완료 |

## 리뷰 3차 반영

`job_retry`의 확인(후속 요약 없음)과 변경(pending)이 한 쓰기 트랜잭션이 아니어서, 사이에 커밋이 후속 요약을 넣으면 유일 제약 오류가 났습니다 (순차 호출은 2차에서 고쳤지만 동시 호출은 남아 있었음).
→ `tx()`(BEGIN IMMEDIATE) 안에서 확인과 변경, 갱신은 `state='failed'`일 때만, 제약 충돌도 정상 응답("되살리지 않음"). 재시도와 커밋을 서로 다른 MCP 서버에서 동시에 30번 보내는 시험으로 재현(고치기 전 매번 실패)한 뒤 고쳤습니다.

## 실패 구간의 한계 (2026-10-18 리뷰 5차 결정)

- 실시간 요약은 **총 1회**를 유지한다. 인프라 장애(Redis 유실 복구 중 실패 확정 등)로 실패해도 다시 등록하지 않는다 — LLM 호출이 이미 시작됐을 수 있고, 지금은 비용 예약·호출 이력 구분이 없다.
- 실패한 구간은 **새 전사가 오면** 다음 요약이 처리 위치부터 읽어 함께 처리한다. 새 전사가 없으면(녹음 막바지) 다시 요약되지 않는다.
- 전사 원문 보존과 실시간 요약 누락은 별개다. 최종 노트 생성은 아직 미구현이라, 빠진 요약을 최종 노트가 자동으로 메운다고 구현상 보장되지 않는다.
- 추가 복구 1회는 별도 개선. 도입할 때는 같은 전사 구간의 복구 횟수를 **영속적으로** 기록해, Redis가 반복 초기화돼도 계속 재등록되지 않게 한다.

## 하지 않은 것

- 요약 주기 조절(20·40·60초)과 "확정 전사 100자 이상·20초 대기" 같은 실행 조건 — 지금은 대기 요약이 허가되는 즉시 실행
- 실제 OpenAI 요약, 화면 알림(outbox), 녹음 종료 때 최종 노트 등록
- 비용 한도 검사 (복구 스캔에 넣을 자리만 표시)
- PG로 옮기기 (같은 제약·조건을 PG 부분 유일 인덱스로)

## 깨지는 변경

`transcript_commit` 응답에 `added` 추가, `coalesced`는 "새 전사가 대기 요약에 합쳐짐"만 뜻함. `transcript_range`는 이 강의 요약 작업의 현재 permit이 있어야 함 (REQUIRE_PERMIT=1). `jobs`에 `lecture_id` 열 추가, `job_reserve_pending`에 실시간 요약 배정 조건 추가 (다른 종류는 그대로). `.gitignore`에 `data/`.
