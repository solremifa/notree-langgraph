## ① Redis 실행 설정과 재시작 복구 (P1)

문제: 복구는 표시 키 `notree:redis-alive`가 **없어지면** 유실로 봤는데, compose 설정은 Redis 기본값(스냅숏 `save 3600 1 300 100 60 10000`, 종료 시 저장)을 그대로 썼다.
"표시 키가 든 스냅숏 저장 → 새 작업 전달 → Redis 죽고 스냅숏으로 복원"이면 표시 키는 있는데 메시지는 없어 복구가 0건, 작업이 멈춘다.

고친 뒤:
- `docker-compose.yml`: `redis-server --save "" --appendonly no`, 볼륨 없음. 설정을 바꿨으면 `docker compose up -d --force-recreate`.
- 표시 키의 값 = 표시를 남길 때의 **Redis run_id**. 표시 키가 없거나 값이 지금 run_id와 다르면 유실로 본다 (프로세스 재시작·스냅숏 복원·장애 조치). 비영속 원칙이라 재시작은 곧 유실이다.

확인:
| 시험 | 결과 |
|---|---|
| (실제 redis-server) 표시 키 든 스냅숏 → 새 작업 전달 → 스냅숏으로 복원 | 고치기 전: 표시 키 있음·메시지 없음·복구 0건 / 고친 뒤: 1건 다시 보내 완료 |
| (실제 redis-server) compose의 `command` 인자를 그대로 읽어 띄우고 쓰기 → 정상 종료 → 재시작 | 비어서 시작, 덤프·AOF 파일 없음 |
| (Docker 컨테이너, 이 저장소의 compose 파일) 쓰기 → `compose restart` / `SHUTDOWN`+`start` / `stop`+`up -d` | 모두 `dbsize=0`, 매번 run_id가 바뀜 |
| (Docker 컨테이너, 예전 compose 설정) 쓰기 → `compose restart` | `save 3600 1 …`, 재시작 뒤 표시 키·Stream 그대로 남음 — 리뷰가 말한 위험의 원인 확인 |

Docker 시험은 레지스트리 접근이 막힌 환경이라 이 머신의 redis-server 7.0.15 바이너리로 만든 로컬 이미지(`redis:7-alpine` 태그)로 돌렸다. compose 파일·컨테이너 재시작 동작은 실제와 같고, 공식 이미지에서의 재확인은 Docker 허브에 닿는 PC에서 하면 된다.

## ② 인용 ID 유일성 (P1)

문제: 저장소는 노트와 전사가 같은 `doc_id`를 쓰는 것을 허용했고, 그래프는 출처 없이 `id`만으로 근거를 찾았다(`sources_for`).
노트 `same`="스택은 LIFO이다", 전사 `same`="힙은 완전 이진 트리이다"로 재현 → 답변은 노트 내용인데 **저장된 인용 원문은 전사**, 상태 completed. LLM이 아니라 코드가 원문을 바꾼 문제.

고친 뒤:
- 계약: `QaHit.id`는 출처(노트·전사·웹) 전체에서 유일해야 한다.
- 그래프: 검색 결과를 받을 때 이미 받은 근거와 ID가 같은데 출처나 원문이 다르면 뒤에 온 것을 거절하고 `skipped`에 남김. 같은 근거의 재검색은 통과.
- 저장소(SQLite `qa_seed`): 같은 과목에서 다른 출처에 이미 있는 ID는 `invalid_args`. PG 검색 문서(`qa_search_docs`)는 `doc_id`가 기본 키라 원래 유일.

시험: 리뷰 순서 그대로 → 저장된 원문이 인용한 노트 그대로, 충돌 기록 / `qa_seed`가 다른 출처의 같은 ID 거절, 같은 출처 덮어쓰기는 그대로.

## ③ 마지막 시도에서 저장 응답 유실 (P2)

문제: "이미 저장됐으면 그래프를 건너뛴다"는 다음 시도가 있을 때만 효과가 있었다. 마지막 시도(또는 전체 마감 직전)에서
`qa_complete`가 저장을 끝내고 응답만 잃으면 질문은 answered, 작업은 failed(시도 한도 초과) → 화면에 따라 성공·실패가 다르게 보임.

고친 뒤: 핸들러가 `done_check`(읽기 전용, `async (ctx) -> bool`)를 함께 등록할 수 있다 (`@handler("qa", done_check=qa_saved)`).
루프는 **다음 시도가 없는 실패**(시도 한도 초과, 마감 초과, 시작 때 이미 마감 지남)를 확정하기 전에 이것을 부르고(최대 5초),
이 작업의 결과가 저장돼 있으면 실패 대신 `job_finish`로 완료를 확정한다. 확인이 실패하면 원래대로 실패 확정. LLM을 다시 부르거나
시도 횟수를 늘리지 않는다. FatalError(질문 삭제 등)는 그대로 실패.
- Q&A의 확인은 `qa_context.answered` (질문이 answered이고 저장한 idem_key가 이 작업 ID).
- 실시간 요약은 확인 도구(`transcript_range`)가 attempted_until을 바꾸는 쓰기라 done_check로 쓰지 않았다. 대신 같은 시도 안에서
  같은 idem_key로 저장을 세 번까지 다시 보내는 기존 처리(PUBLISH_CONFIRM)가 응답 유실을 다룬다.

시험 (고치기 전 코드에서 앞의 둘은 failed):
| 시험 | 결과 |
|---|---|
| 시도 한도 1, 저장 직후 응답 유실 | 작업 done, 시도 1, LLM 1번, 답변 completed |
| 저장 직후 전체 마감이 지나 시간 초과 | 작업 done, 답변 answered |
| 시도 한도 1, 저장 전에 끊김 (반대 경우) | 작업 failed(시도 한도 초과), 답변 없음 |

덧붙여 ①의 `redis_lost`가 `INFO`를 못 쓰는 Redis(fakeredis 시험, INFO를 막은 관리형)에서 매 주기 오류로 멈추던 것을 고쳤다 —
run_id를 못 얻으면 고정값을 써서 표시 키가 있나만으로 판단한다 (이때는 스냅숏 복원을 못 잡는다). ① 커밋 때 전체 시험을 다시 돌리지 않아 놓쳤다.
