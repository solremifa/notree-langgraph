# 진행 상황 (2026-10-18)

"PoC 구현·테스트 완료"는 이 저장소 안에서 SQLite·가짜(또는 로컬) Redis·가짜 LLM으로 테스트가 통과했다는 뜻입니다.
PostgreSQL·실제 업무 데이터·실제 LLM까지 포함한 운영 검증은 아직입니다. 장애 복구는 실제 Redis로 시험했지만 원자성 검증은 SQLite 기준입니다.

## PoC 구현·테스트 완료 (main, 테스트 146개)

**작업 처리 뼈대**
- 작업 등록 → 레인별 배정 → Redis Stream → worker → 완료가 DB에 확정된 뒤 ACK
- 죽은 worker의 작업 회수(XAUTOCLAIM), 체크포인트에서 재개, 늦게 끝난 worker 결과 거절(permit 실행 세대)
- 재시도·실패 규칙과 작업 종류별 실행 정책, 마감 시각, 종료 시 진행 중 작업 마무리
- 누락 의도 다시 보내기, 체크포인트 정리, MCP 도구 계약(`docs/tool-contracts.md` 자동 생성)
- 레인: `qa`(Q&A·채점) / `rt`(실시간 요약) / `batch`. 슬롯 고정이 기본, 빌려 쓰기는 옵션
- 실제 Redis + 프로세스 분리 동작 확인: 정상 경로(Windows)와 worker 인계(Linux) — [기록](measurements/2026-10-17-real-redis/README.md)

**배정·회수·Redis 유실 복구** (2026-10-18, [변경 정리](changes/2026-10-18-dispatch-recovery.md))
- 배정기가 여럿이어도 같은 작업을 두 번 허가하지 않음 (한 트랜잭션 + `WHERE state='pending'`)
- XAUTOCLAIM 탐색 위치를 Stream별로 이어 감, Redis 초기화 뒤 consumer group 재생성
- 전달 세대: Redis 유실을 발견할 때마다 DB가 세대를 올리고 메시지·작업에 기록. 이전 세대 메시지의 시작은 거절, 마지막 전달이 이전 세대인 작업을 다시 보냄 (lease가 살아 있으면 보류 뒤 재확인, 쪽 나누기로 끝까지). 세대 없는 메시지는 기본 거절
- 운영 규칙: 처리 중 메시지를 Stream에서 지우거나 잘라내지 않는다 (XDEL·MAXLEN·XTRIM 금지)

**Redis 실행 상태 모드** (2026-10-18, 코드만 통합 · **기본값 `db` 유지**, [변경 정리](changes/2026-10-18-redis-heartbeat.md))
- `NOTREE_LIVENESS=redis`: 소유 키 + Lua heartbeat 한 번, DB heartbeat 없음. 번호는 DB 실행 세대만 발급, 소유 키는 더 큰 세대만 덮어씀. 최종 쓰기는 DB의 현재 실행 세대만 허용
- 활성화는 별도 결정: 동시 시작 시 시도 한도 소모, Redis 유실 뒤 재계산 비용, 실제 운영 지연을 본 뒤

**실시간 요약 범위 합치기** (2026-10-18, PoC — SQLite·가짜 LLM, [변경 정리](changes/2026-10-18-summary-coalesce.md))
- 강의당 대기 요약 1개(DB 유일 인덱스) + 동시 실행 1개(배정 조건) → 그사이 커밋은 다음 요약 하나로 합쳐짐
- 요약 저장과 위치 이동은 한 트랜잭션, 작업↔강의 연결·실행권·세대 확인, 저장 응답 유실 시 같은 idem_key로 재확인
- 실시간 요약은 **총 1회** 유지. 실패한 구간은 새 전사가 오면 다음 요약이 함께 처리하고, 새 전사가 없으면 다시 요약되지 않는다

**Q&A 그래프** (`notree/graphs/qa/`, 위 95개 중 33개)
- 정책 흐름과 가짜 의존성 기반 테스트 완료: 질문 이해 → 노트 / 전사 / 웹 검색 → 답변 → 인용 검증 → 저장, 시간 예산, 검색 장애 처리, 결과 형식
- **가짜 검색·저장 도구로 worker까지 연결됨** (질문 등록 → qa 레인 → 그래프 → 답변 저장 → 조회, 위 95개 중 11개). 실제 검색·LLM·화면 전달은 진행 전. 실제 검색 품질과 새 프롬프트의 응답 품질은 검증 대상입니다

**Q&A 대화 세션 단기 메모리** (2026-10-20, `feat/qa-conversation-memory` — **main 미머지**, [변경 정리](changes/2026-10-20-qa-conversation-memory.md))
- 대화 시작·종료·만료 도구, 질문 등록에 `conversation_id`, 대화당 진행 중 질문 1개(조건부 갱신), Redis 최근 문답(쌍 단위·세션 세대 키)
- understand부터 이전 문답 사용(검색용 질문·검색어), 모호하면 확인 질문(`확인 필요`). DB 저장 뒤 Redis 반영 실패·종료 경쟁·TTL 만료·Redis 재시작 시험
- 가짜 LLM·가짜 검색 + 가짜/실제 Redis(시험 전용). **실제 모델의 문맥 해석·확인 질문 품질은 미검증**. api 인증은 PoC 수준 그대로

## 개발 순서

1. **Q&A를 끝까지 연결** — 질문 하나가 등록부터 답변 저장·조회까지 끝나는 경로
   1. 검색·저장 도구 계약 확정 — 🔶 main에 **잠정 계약**으로 반영 (`docs/tool-contracts.md`에 "[잠정 · T5 확인 전]" 표시). 화면 담당이 확정 계약으로 의존하기 전에 T5 확인
   2. 가짜 도구로 worker–그래프 연결 (마감·permit·오류 변환·멱등 저장) — ✅ main, [변경 정리](changes/2026-10-17-qa-worker.md)
   3. 실제 검색·저장 연결
   4. 실제 OpenAI로 품질·시간·비용 검증 (인용·부분 답변·시간 초과 포함) — 도구 준비됨: `uv run python -m notree.dev.qa_eval --llm openai`. 주어진 근거로 답하는 능력만 보며, 실제 검색 품질은 아님
   - 순서: 실제 OpenAI(가짜 검색) → 실제 PG 검색 연결 → 실제 강의 데이터로 근거 검색 성공률·"강의 2개 우선 → 부족 시 확장" 평가
   - ✅ 실제 OpenAI(가짜 검색): gpt-4o-mini, 사례 7개 × 3회 × 2번 통과 ([기록](measurements/2026-10-17-openai-qa/README.md)). 정해진 사례의 자동 검사이며 일반 정확도가 아님. 모델의 인용 표시 준수는 다음 측정부터 따로 봄
   - 다음: 실제 PG 검색 연결. 비용 최적화("LLM에 넘길 근거가 그대로면 다시 답하지 않기")는 별도 변경
   - 노트 반영 제안(proposal)과 사용자 승인은 첫 통합에서 뺌
2. 실시간 요약 → 최종 강의노트 → 채점
3. 과목노트 실제 병합 (중복·충돌 판단, 사용자 확인 후 재개)
